# 사전 등록: SFT → RFT → DPO 학습 계획

> **이 문서는 결과를 보기 전에 작성했다.** 판정 기준, 중단 규칙, 예상 실패 모드를 미리 적어
> 나중에 결과에 맞춰 기준을 고치는 것을 막는다. 작성일 2026-08-27.

## 0. 한 줄 요약

로컬 1.5B를 Gemini(30/33) 수준으로 끌어올린다. 두 번의 SFT로 23/33까지 왔고,
**남은 격차가 임계값이 아니라 판별력 문제**임이 오늘 실패 분해로 드러났다.
그래서 모방 학습(SFT)에 더해 **검증 가능한 보상(RFT)과 선호 학습(DPO)**을 얹는다.

## 1. 근거: v4 실패 10건의 정확한 구성

오늘 측정한 것이다. 추측이 아니다.

| 원인 | 건수 | 성격 | 처방 |
|---|---|---|---|
| **전사 오류** (옳은 줄을 골랐는데 오타) | 3 | 샘플링하면 맞는 것이 나옴 | **RFT** |
| **파싱 예외** (반복 생성 루프) | 1 | 디코딩 문제 | 제약 디코딩 |
| 근거 미주장 (있는데 못 알아봄) | 2 | 판별 실패, 과소 | **DPO** |
| 오탐 (없는데 주장) | 3 | 판별 실패, 과잉 | **DPO** |
| 원인 구체성 | 1 | Gemini도 실패 | SFT + 검증 규칙 |

전사 오류의 실제 사례다. `monitor-redis-stream-e2e-latency-35`에서:

```
모델 인용: [2026-08-26 14:10:05.122] [ERROR] [,] --- [pool-1-thread-4] c.g.h.RedisStreamContainerReco...
실제 원문: [2026-08-26 14:10:05.130] [ERROR] [,] --- [pool-1-thread-4] c.g.h.RedisStreamContainerReco...
                          ^^^ 8밀리초
```

**유사도 99%.** 옳은 줄을 정확히 골라놓고 밀리초 두 자리를 잘못 썼다.
**이런 모델을 8번 샘플링하면 그중 하나는 정확히 베낀다.** 이것이 RFT가 확실히 이길 지점이다.

## 2. 왜 SFT만으로는 부족한가

남은 판별 실패가 **과소 2건과 과잉 3건이 동시에** 있다.

두 번째 시도에서 이 축의 곡선을 이미 그렸다.

| 학습 데이터 예:아니오 | 인용 | 오탐 |
|---|---|---|
| 79 : 21 | 11/15 | 44% |
| 70 : 30 | 10/15 | 17% |
| 59 : 41 | 8/15 | 11% |

**70:30이 이 손잡이의 최적점이고 지금 거기에 있다.** 더 돌리면 한쪽을 고치고 다른 쪽이 나빠진다.
즉 **임계값이 아니라 판별을 바꿔야 한다.**

- **SFT는 모방이다.** 좋은 출력의 확률을 올릴 뿐 나쁜 출력을 명시적으로 누르지 않는다.
- **DPO는 같은 입력에 대해 좋은 것과 나쁜 것을 대비시킨다.** 경계 문제에 직접 작용한다.

## 3. 보상 함수 명세 (모든 단계의 중심)

**하나의 함수가 세 역할을 한다: 학습 신호, 평가 종점, 판정 기준.**
`analysis/reward.py`에 새로 만든다. 기존 규칙을 최대한 재사용한다.

시나리오 하나에 대해 0.0 ~ 1.0.

| 항목 | 배점 | 라벨 필요 | 판정 | 재사용할 기존 코드 |
|---|---|---|---|---|
| 형식 유효 | 0.10 | 불필요 | JSON 파싱 성공 + 필드 존재 | `analyzer.parse_analysis` |
| 판정 일치 | **0.50** | **필요** | `evidenceFound` == 기대 판정 | `verification.expects_evidence` |
| 인용 원문 일치 | **0.40** | 불필요 | 인용이 로그 **한 줄 전체와 정확히 일치** | `verification.CitationIsVerbatim` |
| 원인 구체성 | **0.0** | - | **사전 검사 미통과로 제외** (아래) | 진단용으로만 유지 |
| 근거 없을 때 원인 부재 | -0.30 | 불필요 | 근거 없음인데 원인을 말하면 감점 | `verification.NoCauseWithoutEvidence` |

구체성 항목을 뺀 뒤 남은 셋에 재분배해 만점이 1.0이 되게 했다.

**근거 없음이 정답인 시나리오**에서는 인용과 구체성 항목을 만점 처리한다(해당 없음).
그러지 않으면 음성 시나리오의 최대 점수가 0.5가 되어 양성과 척도가 어긋난다.

### 신규 규칙: CauseNamesEvidenceComponent

지금까지 "원인 구체성"은 judge만 판정할 수 있어서 학습 표적으로 삼지 못했다. 코드로 옮긴다.

```
인용한 로그 줄에서 식별자를 추출한다:
  - 로거명 (예: c.global.redis.EventDispatcher)
  - 컨슈머 클래스명 (예: LadderDrawCommandEventConsumer)
  - 스트림 키 (예: laddergame, room:join)
  - 스레드명의 스트림 부분 (예: redis-stream-thread-pool-laddergame1 → laddergame)
원인 문장(rootCauseHypothesis)에 그중 하나라도 등장하면 통과.
```

**검증 결과 (실행 완료): 배점에서 제외했다.**

judge 판정과의 일치율이 **38%**였다(기준 60%). 어긋난 131건 중 **123건이 규칙이 더 엄격한**
방향이었다. judge는 클래스 이름이 아니라 메커니즘을 한국어로 짚어도 구체적이라고 본다.

```
원인: "Oracle Object Storage 서비스와의 통신 문제로 읽기 시간 초과"   → judge 통과
로그의 이름들: OracleObjectStorageService, QrCodeService             → 규칙 탈락
```

타당한 원인 서술인데 이름 일치를 요구해 떨어뜨린 것이다. **조작적 정의가 틀렸다.**
같은 데이터에 맞춰 규칙을 고치면 맞추기가 되므로 하지 않았다. 규칙은 진단용으로 남기고,
다시 설계할 때는 이 데이터가 아닌 곳에서 검증한다.

## A단계 결과 (2026-08-27 실행 완료)

**게이트 통과.** v4 그리디 0.788 → best-of-8 0.958, 여유 **+0.170** (기준 +0.05).

측정 도구가 기존 endpoint 수치를 네 팔 모두 재현해 정의가 맞음을 확인했다
(base 3/15·3/18, v2 11/15·8/18, v3 8/15·2/18, v4 10/15·3/18).

### 여유의 정체: 유형마다 다르다

8개 샘플 중 판정을 맞힌 개수를 세니 하나의 답이 아니었다.

| 유형 | 건수 | 판정 정답 | 만점 | 해석 |
|---|---|---|---|---|
| 전사 오류 | 3 | **7~8/8** | 1~3/8 | 판정은 확실히 안다. 인용만 흔들림 |
| 파싱 예외 | 1 | 7/8 | 6/8 | 형식만 가끔 깨짐 |
| 근거 미주장 | 2 | 4~5/8 | 3~4/8 | 사실상 무작위 |
| 오탐 | 3 | **0~3/8** | 0~2/8 | 틀리는 쪽을 일관되게 선호 |

**앞의 4건은 RFT가 고칠 수 있고, 뒤의 5건은 고를 만점 샘플 자체가 없다.**
`http-5xx-ratio-high-sparse-logs`는 8번 다 틀린다.

### 여기서 철회한 규칙

측정 직후 "만점 샘플이 6개 이상인 프롬프트만 학습에 쓴다"는 규칙을 제안했다가 **철회했다.**
전사 오류 3건의 만점이 1/8, 2/8, 3/8이므로 그 규칙은 **RFT가 고쳐야 할 것을 정확히 배제한다.**
Rejection sampling의 목적이 드물게 맞는 행동을 흔하게 만드는 것인데 정반대로 건 셈이다.

### 대신 세운 원칙: 라벨이 필요한 항목과 아닌 항목을 나눈다

| 항목 | 배점 | 라벨 필요 | 뜻 |
|---|---|---|---|
| 형식 | 0.10 | 불필요 | 추론 시점에도 검증 가능 |
| 인용 원문 일치 | 0.40 | 불필요 | 추론 시점에도 검증 가능 |
| 판정 | 0.50 | **필요** | `expected`와 비교해야 함 |

**형식과 인용에서 얻은 여유는 배포 가능한 개선이다.** 라벨 없이 고를 수 있기 때문이다.
**판정에서 얻은 여유는 신탁 상한이다.** 정답을 알려주고 고른 값이라 추론 시점에 회수되지 않는다.
판정이 4/8로 흔들리는 시나리오의 "최고 샘플"은 운 좋게 맞은 것이다.

### 보상 설계에서 명시할 것

판정 항목은 **접지 전 원 주장**을 본다. 그래서 인용 검증에 걸려 강등될 허위 주장도
판정 오답으로 센다. 보상 기준 판정 오답 10건, 운영 기준(접지 후) 오탐 3건이다.
의도한 것이지만(허위 주장 자체를 억제) **보상이 운영 동작보다 엄격하다.**
보상 순위와 judge 총점 순위가 갈릴 수 있다(실제로 v3 0.867 > v4 0.788인데 judge는 v4가 높다).

### 분석 중 잡은 자기 오류

점수 0.5를 판정 정답으로 셌다가 정반대 결론을 낼 뻔했다. 실제 조합을 출력해보니
판정 정답은 0.6 이상이었다(0.5는 판정 오답 + 나머지 만점).
**연속 점수를 이진 판정으로 되돌릴 때는 매핑을 실측해야 한다.**

## B단계: 대조 쌍 SFT (하루, GPU 80분)

**목적**: RL의 출발 정책을 개선한다. 정책이 나쁘면 RL이 낭비된다.

### 핵심 아이디어: 대조 쌍

지금 학습 데이터는 독립 시나리오의 나열이라 **로그 표면 패턴**으로 정답을 낼 수 있다.
로그를 고정하고 알림만 바꾸면 그게 불가능해진다.

```
같은 로그 2줄 + 알림 A  →  근거 있음   (이 로그가 A를 설명함)
같은 로그 2줄 + 알림 B  →  근거 없음   (같은 로그인데 B와는 무관함)
```

골든셋에는 이런 대조군 쌍이 4개 있고 그것이 "내용은 보고 시각은 안 본다"를 입증했다.
**학습 데이터에는 하나도 없다. 지금 가장 큰 구멍이다.**

### 데이터 구성 목표

| 종류 | 건수 | 만드는 법 |
|---|---|---|
| 기존 | 135 | 그대로 |
| **대조 쌍** | 60쌍 = 120 | 에이전트 생성. 쌍의 두 항은 로그가 **완전히 동일**해야 함 |
| 실패 3종의 hard negative | 30 | `sparse-two-lines`, `http-5xx-sparse-logs`, `target-down-mysql-exporter` 변형 |
| **합계** | **약 285** | 예:아니오 = 70:30 유지 |

### 실행

```bash
# 1) 대조 쌍 생성 (에이전트, GPU 0)
#    프롬프트는 raw/prompts-pair/ 에 생성. 쌍은 같은 파일에 두 시나리오로 기록.

# 2) 적재 (모든 기존 배치와 중복 비교)
.venv312/bin/python -m synthesis.ingest_cli --label train-pair --input-dir raw/pair \
  --compare-dirs candidates/train-all candidates/train-neg --min-interval 1.2

# 3) 교사 생성 + 검증 (새 규칙 포함)
.venv312/bin/python -m training.build_cli --label sft-pair \
  --scenarios-dir candidates/train-pair --min-interval 1.2

# 4) 병합 후 감사 + 길이 가드
.venv312/bin/python -m training.audit_cli \
  --candidate-dirs candidates/train-all candidates/train-neg candidates/train-pair \
  --data-dir training/data/sft-v5

# 5) 학습 (에폭을 4.7로 고정: 242 train이면 1140 iter)
.venv312/bin/python -m mlx_lm lora \
  --model mlx-community/Qwen2.5-1.5B-Instruct-4bit \
  --train --data training/data/sft-v5 --adapter-path training/adapters/sft-v5-s1 \
  --num-layers 16 --batch-size 1 --iters 1140 --learning-rate 1e-4 \
  --max-seq-length 3200 --seed 20260826 --save-every 1140 \
  > ~/scratch/lora-v5.log 2>&1
```

**주의**: 대조 쌍은 `similarity.signature`가 **중복으로 판정한다**(시그니처가 알림 본문을 안 보므로).
적재 전에 시그니처에 `alert.summary`와 `alert.description`을 포함하도록 고쳐야 한다.
**이것을 안 고치면 대조 쌍이 전부 탈락한다.** B단계 첫 작업이다.

### 사전 등록 기준 (2026-08-28 실행분)

**통제군은 v3다.** v3는 59:41로 비율만 음성 쪽으로 옮긴 팔이고 대조 쌍이 없다.
신규 팔은 52:48로 **더 음성 쪽인데** 대조 쌍이 들어간다. 비율 효과만이라면
v3의 인용 8/15보다 낮아야 한다.

| | 기준 |
|---|---|
| **주 종점** | 평균 보상. v3(0.867) 대비 짝지은 Wilcoxon |
| **핵심 판정** | **인용이 v3의 8/15를 넘는가.** 비율로 설명되지 않는 지점 |
| 성공 | 인용 10/15 이상 유지하며 오탐(원 주장) 7/18 → 4/18 이하 |
| 부분 | 오탐은 내려갔으나 인용도 하락 → 비율 곡선과 구별 안 됨 |
| 실패 | 오탐 그대로 |

**해석 시 구분할 것.** 대조 쌍은 구조상 균형(+19/+19)이라 비율을 거의 안 움직인다.
비율을 70:30에서 52:48까지 끌어내린 것은 **함정 15건**이다.

### 결과 보기 전에 적는 예측: 부분 성공일 것 같다

SFT는 샘플을 독립적으로 학습한다. 손실에 "이 둘은 알림만 다르다"는 항이 없고,
batch_size가 1이라 **쌍의 두 항이 같은 그래디언트 스텝에 들어가지 않는다.**
기대하는 것은 "로그가 같은데 정답이 다른 샘플이 있으면 로그 패턴만으로는 둘 다 맞힐 수
없다"는 **데이터 통계를 통한 암묵적 압력**이고, 규모도 166건 중 38건(23%)이다.

개입이 교란(70:30 → 52:48)보다 약해 보인다. 빗나가면 대조 쌍이 예상보다 강하다는 뜻이다.

**다음에 더 세게 거는 방법**: 쌍을 두 번씩 넣어 가중치를 올리거나, 그래디언트 누적으로
쌍을 같은 스텝에 넣는다. 이번 실행에는 넣지 못했다.

## C단계: RFT + 제약 디코딩 대조 (반나절, GPU 2시간)

Rejection Sampling Fine-Tuning. **검증 가능한 보상으로 배우는 첫 단계다.**

### 원리

```
SFT 모델에서 프롬프트마다 온도 0.8로 8개 샘플링
  → 각 샘플을 보상 함수로 채점
  → 프롬프트마다 최고 보상 샘플만 남김 (보상이 1.0에 미달해도 최고면 채택)
  → 그것으로 다시 SFT
```

### 왜 제약 디코딩 팔을 함께 두는가

**RFT가 겨냥하는 4건은 제약 디코딩이 학습 없이 고칠 수 있다.** 인용을 주어진 로그 줄
중 하나로만 생성하게 강제하면 오타가 원천적으로 불가능하고, JSON 문법을 강제하면
반복 생성 루프가 안 나온다. mlx-lm의 `generate_step`이 `logits_processors`를 받으므로
구현 가능하다.

이걸 숨기고 RFT만 하면 정직하지 않다. 그래서 세 팔을 나란히 둔다.

| 팔 | 방법 | 비용 |
|---|---|---|
| v4 (그리디) | 현재 | 측정 완료 |
| **v4 + 제약 디코딩** | 학습 없음 | 2시간 구현 |
| **v4 + RFT** | 학습 | 반나절 |

답하려는 질문은 이것이다.

> 코드로 강제할 수 있는 행동을 학습으로 가르치면 무엇이 더 생기는가?

제약이 이기면 "이 실패는 학습 문제가 아니었다"가 결론이고, RFT가 비슷하거나 나으면
"학습은 제약이 못 미치는 곳까지 일반화한다"가 결론이다. 후자의 근거는 **온폴리시**다.
교사(Gemini) 출력을 흉내 내는 것과 자기 출력 분포에서 고쳐지는 것은 다르고,
후자가 자기 실패에 더 정확히 작용한다. **둘 다 보고할 가치가 있는 결과다.**

### 실행

```bash
# 배치 8로 샘플링 (실측: 건당 1.7초, 1936건이면 약 55분)
# 50 프롬프트씩 끊어 저장하므로 중단해도 이어서 가능
.venv312/bin/python -m training.rft_sample --adapter training/adapters/sft-v5-s1 \
  --scenarios-dir candidates/train-pair --samples 8 --temp 0.8 --batch 8 \
  --chunk 50 --out training/data/rft-samples

.venv312/bin/python -m training.rft_build --samples training/data/rft-samples \
  --out training/data/rft-v1 --min-reward 0.0 --keep top1

.venv312/bin/python -m mlx_lm lora --train --data training/data/rft-v1 \
  --model mlx-community/Qwen2.5-1.5B-Instruct-4bit \
  --adapter-path training/adapters/rft-v1-s1 \
  --num-layers 16 --batch-size 1 --iters 940 --learning-rate 1e-4 \
  --max-seq-length 3200 --seed 20260826
```

### 사전 등록 기준

주 종점은 평균 보상이고, 인용 통과를 보조로 본다.

| 판정 | 조건 | 다음 |
|---|---|---|
| **성공** | RFT의 **인용 통과 13/15 이상** (v4는 10/15) | D단계로 |
| 부분 | 11~12/15 | D단계로 가되 부분 확인으로 기록 |
| **실패** | 10/15 이하 | 전사 오류 가설 기각 |

**제약 디코딩과의 대조도 사전에 적어둔다.**

| 결과 | 해석 |
|---|---|
| 제약 > RFT | 이 실패는 학습 문제가 아니었다. 정직하게 그렇게 쓴다 |
| RFT ≥ 제약 | 학습이 강제된 행동 밖으로 일반화했다 |
| 둘 다 실패 | 인용 문제가 디코딩도 학습도 아닌 다른 데 있다 |

오탐은 이 단계에서 **악화되지 않기만 하면 된다**(3/18 유지). 오탐은 D단계의 표적이다.

### RFT 표본 선별 규칙

- 프롬프트마다 8개를 뽑아 보상으로 채점하고 **최고 보상 샘플 하나**를 채택한다
- 만점 샘플 개수로 프롬프트를 거르지 **않는다**(위에서 철회한 규칙)
- **학습 프롬프트에서의 분포를 먼저 잰다.** 평가셋의 분포가 학습 프롬프트에도
  성립한다는 보장이 없다. C단계 첫 작업이다

## C단계 재등록 (2026-08-28, v6 기준)

원래 기준(인용 13/15 이상)은 v4 시절 것이라 v6에 안 맞는다. v6는 이미 제약 디코딩과
합쳐 13/15다. **결과를 보기 전에 다시 못박는다.**

### 게이트 결과: 경계

```
v6, 신규 프롬프트 40종(학습 미사용): 그리디 0.910 → best-of-8 0.945   여유 +0.035
그리디 만점 32/40 (80%),  샘플링이 그리디를 이기는 프롬프트 5종
```

사전 등록 기준상 **경계(+0.02~0.05)**다. 원래 조치는 k=16 재확인이었으나 그러지 않는다.
축별로 뜯어보니 게이트가 낮은 이유가 표본 수가 아니라 **프롬프트 구성**이었다.

| 축 | 그리디 만점률 |
|---|---|
| compound-cause | 7/12 (58%) |
| stale-reingested | 1/2 |
| partial-relevance | 1/2 |
| positive-dense | 9/10 |
| **near-miss / unrelated-trap / sparse-evidence** | **전부 100%** |

**어제까지 최대 약점이던 오탐 축 세 개가 전부 100%다.** 함정 데이터가 그 축을 메웠고,
그래서 신규 프롬프트 40종의 절반 가까이가 RFT에 쓸모없는 것(이미 만점)이 됐다.

### 더 중요한 발견: 보상이 남은 실패의 3분의 2를 못 본다

v6c가 평가셋에서 틀리는 6종의 성격이다.

| 성격 | 건수 | 보상이 채점하나 |
|---|---|---|
| 근거 미주장 | 2 | 부분적 |
| **원인 오진/구체성** | **2** | **못 함** (구체성 규칙을 38% 일치로 제외했다) |
| **환각 (조치에 없는 로그 언급)** | **1** | **못 함** (조치 필드를 안 본다) |
| 오탐 | 1 | 함 |

**RFT는 보상을 최대화하는 방법이므로 보상이 안 보는 것을 고칠 수 없다.**
지금 남은 실패의 3분의 2가 그렇다. 이것이 RFT 설정보다 큰 병목이다.

그리고 실패한 것들의 로그가 길다(8줄, 9줄, 8줄). 평가셋 평균은 2~4줄이다.
**로그가 많아지면 근거를 못 찾거나 증상을 원인으로 착각한다.**

### 그럼에도 실행하는 이유와 새 기준

사전 등록된 실험을 끝까지 돌리고 정직하게 보고하는 것 자체가 산출물이다.
데이터가 이미 있고 30분이면 끝난다. **기대는 낮다.**

| 판정 | 조건 |
|---|---|
| 성공 | 보상 0.906 → **0.925 이상** AND 오탐 1/18 유지 AND 인용 9/15 이상 유지 |
| 부분 | 보상 상승하나 0.925 미만 |
| 실패 | 보상 하락 또는 오탐 증가 |

**예측: 부분 성공 또는 무효과.** BoN 여유가 +0.035뿐이고 RFT는 그 일부만 회수한다.
학습 가능한 35종 중 30종이 이미 그리디 만점이라 사실상 자기증류에 가깝다.

## D단계: DPO (하루, GPU 100분 + 구현 시간)

**mlx-lm에 DPO가 없다. 직접 구현한다.** 이것이 "딥러닝 기초를 직접 구현해 증명하라"를 채운다.

### 데이터: 검증기가 선호 라벨을 매긴다

C단계에서 이미 뽑아둔 8개 샘플을 재사용한다. 추가 생성 비용 0.

```
프롬프트마다:
  chosen   = 교사(Gemini) 출력 중 검증을 통과한 것
  rejected = 모델의 최저 보상 샘플
  단, 두 보상 차이가 0.2 미만인 쌍은 버린다 (신호가 약함)
```

**사람이 아니라 코드가 선호를 매긴다. RLHF 알고리즘 위에서 RLVR을 하는 것이다.**

### chosen을 자기 샘플이 아니라 교사로 바꾼 이유 (2026-08-28 수정)

원래 설계는 `chosen = 보상 최고 샘플`이었다. **모델이 8번 다 틀리는 프롬프트에서는
chosen이 없어 가장 어려운 경계를 통째로 건너뛴다.**

그리고 C단계(RFT)가 정확히 그 함정으로 실패했다. "최고 보상이 만점인 것만 쓴다"는
필터가 어려운 쪽(근거 있음, 특히 후보가 여럿인 5xx)을 비대칭으로 걸러내, 판정 비율이
60%에서 56%로 밀렸고 그 축에서 무너졌다.

교사를 chosen으로 쓰면 **항상 존재하고 어려운 것도 빠지지 않는다.**

### C단계 실패에서 가져올 것

1. **판정 비율 왜곡을 확인한다.** 버려지는 쌍이 한쪽에 몰리는지 학습 전에 센다
2. **원 분포를 덮지 않게 한다.** DPO는 참조와의 거리를 beta로 억제하지만,
   beta가 낮으면 SFT 이어학습과 같은 일이 난다. beta 0.1로 시작하고 무너지면 올린다

### 손실 함수

```
L = -log σ( β · [ (log π(y_w|x) - log π_ref(y_w|x))
                - (log π(y_l|x) - log π_ref(y_l|x)) ] )

β = 0.1 (기본값)
π     = 학습 중인 정책 (LoRA 어댑터 적용)
π_ref = 참조 정책 (B단계 SFT 모델, 고정)
로그 확률은 **완성 토큰에만** 계산한다 (프롬프트 부분 마스킹)
```

### 구현 메모

- **참조 로그 확률을 미리 계산해 디스크에 저장한다.** 그러면 학습 중 참조 모델을
  메모리에 안 들고 있어도 되고, 스텝당 forward가 4회에서 2회로 준다.
- 사전 계산: 484 forward, 약 10분
- 학습: 726 스텝 × 약 8초 = 약 97분
- 파일: `training/dpo.py` (손실 + 학습 루프), `training/dpo_cli.py`

### 사전 등록 기준

| 판정 | 조건 |
|---|---|
| **성공** | **오탐 2/18 이하** AND 인용이 C단계 수준 유지 |
| 부분 | 오탐은 내려갔으나 인용도 하락 → 트레이드오프 곡선으로 기록 (두 번째 시도와 같은 구조) |
| 실패 | 오탐 그대로 → 판별 문제가 DPO로 안 풀린다는 결론 |

## 4. 측정과 통계

### 종점

**주 종점: 평균 보상 (연속값).** 짝지은 Wilcoxon 부호순위 검정.

이진 PASS로 세면 정보를 버려서 검정력이 없다. 오늘 계산한 것이다.

```
개선 3 / 악화 0 → p = 0.2500   ← 완벽해도 유의하지 않음
개선 6 / 악화 0 → p = 0.0312
```

연속 종점이면 중간 크기 효과(d=0.5)를 잡는 데 필요한 표본이 약 34쌍이라
**지금 33종으로 충분하다.** 평가셋을 늘리지 않아도 된다.

### 보조 종점 (전부 judge 없이 코드로)

- 인용 통과 (양성 15종)
- 오탐 (음성 18종)
- 변별력 J = TPR - FPR
- 형식 실패 건수

### judge 총점

**단계마다 매번 재지 않는다.** 최종 팔 하나만 Gemini와 같은 조건으로 잰다(33콜).
judge는 변동이 있고 API 비용이 들며, 우리 판정 기준은 보상 함수다.

### 다중비교

주 종점은 **평균 보상 하나**다. 보조 종점은 탐색적이며 그렇게 표기한다.
최종 보고에는 Holm 보정 후 p값을 병기한다.

## 4-b. 상시 제약: RL 단계는 신규 프롬프트가 선행되어야 한다

**C단계(RFT)와 D단계(DPO)는 SFT에 한 번도 쓰이지 않은 프롬프트에서만 샘플링한다.**

자기 학습 데이터에 자기를 샘플링하면 암기를 재는 것이지 능력을 재는 것이 아니다.
2026-08-27에 실측했다.

```
학습에 쓴 프롬프트: 그리디 만점 106/147 (72%)
평가셋(안 쓴 것):   그리디 만점  19/33  (58%)
```

RFT는 드물게 맞는 행동을 골라 흔하게 만드는 방법인데, 이미 외운 프롬프트에서는
그리디가 이미 만점이라 고를 것도 배울 것도 없다. 실제로 이걸 모르고 40분을 버렸다.

**매 SFT 라운드가 프롬프트를 소진하므로 RL 단계마다 신규 생성이 선행된다.**
생성은 에이전트로 하므로 무료다. SFT에서 프롬프트를 떼어내 보류하는 것보다,
그때그때 새로 만드는 편이 SFT 데이터를 안 깎아 낫다.

## 6. 하지 않기로 한 것과 그 이유

### GRPO

온라인 생성이 학습 루프 안에 있어 스텝마다 8건을 뽑아야 한다. PyTorch MPS로 가면
배치 생성 이점도 사라진다. 이 맥북에서 며칠짜리다.

**RFT와 DPO가 오프라인이라 생성과 학습이 분리되고, 그래서 맥북에서 된다.**
타협이 아니라 하드웨어에 맞는 선택이며, "왜 GRPO를 안 골랐나"를 비용으로 설명할 수 있다.
보상 함수는 프레임워크 중립으로 만들어, GPU가 생기면 그 자리에서 시작할 수 있게 둔다.

### 스키마 변경 (`evidenceLine` → `evidenceIndex`)

**RL 실험이 끝난 뒤 별도 팔로 넣는다.** 두 가지 이유다.

1. 먼저 넣으면 인용 검증이 무의미해져 **RLVR의 가장 좋은 보상 신호를 잃는다.**
2. 마지막에 넣으면 결론이 이렇게 된다: **"학습으로 여기까지 끌어올렸고, 그다음 스키마
   하나를 바꾸니 그 노력의 절반이 불필요해졌다."** 학습만 자랑하는 것보다 성숙한 이야기다.

### 프롬프트에 컴포넌트 그래프 주기

**세 번 시도했고 세 번 다 실패했다.** 오늘 측정한 것이다.

| 변형 | 준 것 | judge 총점 | 오탐 | 실패 방식 |
|---|---|---|---|---|
| production | 없음 | 30/33 | 1/18 | (기준) |
| mechanism-aware | 추상 규칙 | - | - | 과소 특정 |
| graph-aware | 구체적 사실 | 27/33 | 5/18 | **과잉 연결** |
| graph-strict | 사실 + 배제 전용 제약 | 27/33 | 3/18 | **과잉 배제** |

**프롬프트로 지식을 주면 판정 성향이 한쪽으로 밀린다.** 제약으로 막으면 반대로 밀린다.
가운데를 못 맞춘다.

**대신 데이터로 준다.** 학습 데이터의 모든 샘플이 "언제 연결하고 언제 연결하지 않는가"를
함께 보여주므로 지식과 보정이 같이 들어간다. 70:30이 작동한 이유와 같은 구조다.
**대조 쌍(B단계)이 정확히 그 형태다.**

## 8. 시간과 발열

실측 기준이다.

```
단건 생성        5.5초
배치 8건 생성    건당 1.7초  (3.2배속)
SFT 학습         iter당 약 4초 (batch 1, seq 3200)
```

| 단계 | GPU 시간 | 연속 블록 최대 |
|---|---|---|
| A 측정 | 15분 | 15분 |
| B SFT | 80분 | 80분 |
| C RFT 샘플링 | 55분 | **50 프롬프트씩 끊음** |
| C RFT 학습 | 63분 | 63분 |
| D DPO 사전계산 | 10분 | 10분 |
| D DPO 학습 | 97분 | 97분 |
| **합계** | **약 5시간** | |

오늘 한 것이 GPU로 약 2.5시간이었다. **이 계획은 오늘의 2배이고, 며칠에 나누면
하루치가 오늘과 비슷하다.** 모든 단계는 중간 저장으로 끊어서 실행할 수 있다.

메모리는 문제가 아니다. 1.5B 4비트가 약 1GB이고 DPO에서 참조 모델을 더해도 2GB다.
참조 로그 확률을 사전 계산하면 그마저 필요 없다.

## 10. 내일 시작 순서

