# 대조 쌍 학습과 Gemini 기준값

사전 등록한 계획([13번](13-사전등록-학습-계획.md))의 B단계 실행과, 그동안 없던
**참조 시스템의 주 종점 값**을 확보한 기록이다.

## 1. 결과

| 팔 | judge 총점 | 보상 | 인용 | 오탐 |
|---|---|---|---|---|
| **Gemini 2.5 Flash** | **30/33 (91%)** | **0.985** | 15/15 | 1/18 |
| 1.5B 학습 전 | 15/33 (45%) | 0.570 | 1/15 | 15/18 |
| 1.5B 첫 번째 시도 | 19/33 (58%) | 0.800 | 10/15 | 9/18 |
| 1.5B 두 번째 시도 (v4) | 23/33 (70%) | 0.788 | 10/15 | 7/18 |
| v4 + 제약 디코딩 | - | 0.824 | 13/15 | 7/18 |
| v6 (대조 쌍 + 함정) | - | 0.906 | 9/15 | 1/18 |
| **v6 + 제약 디코딩** | **27/33 (82%)** | **0.955** | 13/15 | **1/18** |

인용은 접지 파이프라인 기준(로그의 부분 문자열), 오탐은 접지 전 원 주장 기준이다.
보상의 인용 항목은 더 엄격한 전체 줄 일치를 쓴다.

**Gemini까지의 격차를 judge 총점에서 15점 중 12점(80%) 좁혔다.**
**오탐은 1/18로 동률이다.**

## 2. 주 종점에 기준값이 없었다

오늘 아침까지 보상 함수를 로컬 모델만 잴 수 있게 만들어 두었다.
**참조 시스템에서 계산할 수 없는 지표를 주 종점으로 삼고 있었던 것이다.**
0.955가 좋은 값인지 나쁜 값인지 말할 방법이 없었다.

`reward_cli --gemini`를 추가해 같은 보상으로 쟀다. **Gemini 0.985.**
격차 0.030은 시나리오 하나 남짓이다.

같은 실수를 이 프로젝트에서 두 번 했다. 두 번째 시도 때도 judge 총점을 안 재서
Gemini와 나란히 놓지 못했고, 33콜을 더 써서 채웠다. **비교하려면 잣대가 양쪽에
닿아야 한다**는 것이 두 번 확인됐다.

## 3. 두 시스템은 서로 다른 것을 틀린다

judge 기준 실패를 맞대어 보면 겹치는 것이 하나뿐이다.

| | 시나리오 |
|---|---|
| 둘 다 틀림 (1) | `outbox-deadletter-publish-failures` |
| **Gemini만 틀림 (2)** | `outbox-dead-letter-high-33`, `redis-stream-e2e-latency-27` |
| v6c만 틀림 (5) | `app-error-log-spike-19`, `error-spike-cardgame-select-burst`, `error-spike-roomjoin-current-window`, `heap-high-sparse-unrelated-errors`, `redis-stream-e2e-latency-35` |

**총점이 27 대 30인 것이 "3종 뒤처진다"를 뜻하지 않는다.** 두 시스템의 강점이 다르다.

Gemini가 틀리는 둘은 **말을 너무 많이 해서** 틀린다(무관한 로그를 근거로 인정, 무관한 원인을
끼워 넣음). 자제하도록 학습시킨 모델이 그 축에서 유리하다.

## 4. 대조 쌍 학습 (B단계)

### 데이터

| 종류 | 건수 | 성격 |
|---|---|---|
| 기존 | 135 | 그대로 |
| **대조 쌍 19쌍** | 38 | 로그를 고정하고 알림만 바꿈. **구조상 균형(+19/+19)** |
| **오탐 함정** | 15 | 희소 근거 8, 인프라 계층 7. **비율 손잡이** |
| 합계 | 188 | 예 98 (52%) / 아니오 90 (48%) |

교사 채택률 **53/53 (100%)**. 기존 배치가 85~94%였던 것에 비해 높다.
중복 감사 4겹 0건, 길이 가드 통과.

### 대조 쌍이란

```
같은 로그 2~4줄 + 알림 A  →  근거 있음   (이 로그가 A를 설명한다)
같은 로그 2~4줄 + 알림 B  →  근거 없음   (같은 로그인데 B와는 무관하다)
```

로그를 고정하면 **로그 표면 패턴만으로는 둘 다 맞힐 수 없다.** 알림과 로그의 관계를
봐야만 맞힐 수 있게 강제하는 것이다. `synthesis/pairing.py`가 쌍의 `logSamples`가
바이트 단위로 같은지 검사한다. 이 검사가 없으면 생성기가 로그를 미묘하게 바꿔도 통과해
전제가 조용히 무너진다.

### 사전 등록 판정: 부분 성공

**통제군은 v3다.** v3는 59:41로 비율만 음성 쪽으로 옮긴 팔이고 대조 쌍이 없다.
v6는 52:48로 **더 음성 쪽인데** 대조 쌍이 들어간다.

| | 비율 | 대조 쌍 | 인용 | 오탐 |
|---|---|---|---|---|
| v3 (통제) | 59:41 | 없음 | 8/15 | 2/18 |
| v6 | 52:48 | 19쌍 | 9/15 | 1/18 |

**차이가 각각 1건이다.** 방향은 대조 쌍 가설과 맞지만(더 음성 쪽 비율인데 인용이 높다)
**이 크기는 노이즈와 구별되지 않는다.** 부호검정 p = 0.75.

**"대조 쌍이 효과가 있었다"고 말할 수 없다.**

### 결과 보기 전에 적은 예측이 맞았다

> SFT는 샘플을 독립적으로 학습한다. 손실에 "이 둘은 알림만 다르다"는 항이 없고,
> batch_size가 1이라 쌍의 두 항이 같은 그래디언트 스텝에 들어가지 않는다.
> 개입이 교란(70:30 → 52:48)보다 약해 보인다.

부분 성공으로 나왔다. 대조 쌍은 **데이터 통계를 통한 암묵적 압력**일 뿐 손실에 명시되지
않는다. 다음에 더 세게 걸려면 쌍을 두 번씩 넣거나 그래디언트 누적으로 쌍을 같은 스텝에
넣어야 한다.

### 확실한 것은 함정 데이터의 효과다

**오탐 7/18 → 1/18.** 7건 차이라 노이즈로 보기 어렵다.
겨냥한 축(희소 근거, 인프라 계층)이 정확히 작동했다.

**인프라 계층은 이 프로젝트에서 학습 커버리지가 0이던 축이다.** 어제 진단하고
오늘 7건을 만들어 넣었다. "실제 실패를 겨냥한 데이터가 작동한다"는 일관된 발견의 반복이다.

다만 대조 쌍과 함정을 같은 팔에 넣었으므로 **개별 기여는 분리되지 않았다.**
분리하려면 팔이 하나 더 필요하다.

## 5. 제약 디코딩의 가치는 모델의 판별력에 달려 있다

어제 제약 디코딩을 "순개선이 아니다"라고 결론지었다. v4에서 인용은 올랐는데(10→13)
오탐이 늘었기 때문이다. 원인은 **접지 검증이 허위 주장을 우연히 막고 있었던 것**이었다.

그렇다면 **허위 주장이 적은 모델에서는 벗겨질 방어가 없다.** 이걸 예측으로 적고 쟀다.

| | 허위 주장 | 제약 후 인용 | 제약 후 오탐 |
|---|---|---|---|
| v4 | 7/18 | 10 → 13 | 7 → 7 (접지 후로는 3 → 7) |
| **v6** | **1/18** | **9 → 13** | **1 → 1** |

**예측대로 나왔다.** v6에서는 제약이 순이득이다(보상 0.906 → 0.955).

**즉 두 개입이 상호작용한다.** 판별이 나쁜 모델에 제약을 걸면 가려져 있던 오탐이 드러나
손해이고, 판별이 좋은 모델에 걸면 이득이다. 순서가 중요하다.

### 구현 중 잡은 버그 둘

첫 시도에서 파싱 실패가 0에서 3으로 늘었다.

**하나. 제약이 빈 인용을 막았다.** `evidenceFound`가 false면 `evidenceLine`은 빈 문자열이어야
하는데, 제약이 무조건 로그 줄을 시작하게 강제했다. **제약의 목적은 날조를 막는 것이지
인용을 강제하는 것이 아니다.**

**둘. 인용 뒤에 반복 생성에 빠졌다.** 실제 출력이 이랬다.

```
...Unable to acquire JDBC Connection" "evidenceLine: [2026-08-26 11:20:02.
```

인용은 정확히 끝냈는데 필드를 다시 쓰기 시작한다. 긴 줄을 강제로 통과시킨 뒤 모델이
분포 밖으로 나간 것이다. `evidenceLine`은 스키마의 **마지막 필드**라 값이 닫히면 `}`밖에
올 수 없다. 제약을 거기까지 확장하니 파싱 실패가 3에서 0이 되고 인용도 10에서 13으로 올랐다.

## 6. 자체 호스팅의 두 번째 논거

지금까지 자체 모델의 논거는 "데이터가 밖으로 안 나간다" 하나였다. 하나가 더 생겼다.

> **제약 디코딩은 로컬 모델만 쓸 수 있다.** Gemini는 API 뒤에 있어 로짓을 건드릴 수 없다.

"인용은 반드시 실제 로그 줄이어야 한다"를 **모델에게 부탁하는 대신 강제할 수 있다.**
운영 도구에서 이 차이는 작지 않다. 부탁은 확률이고 강제는 보장이다.

이 비교가 공정한지 물을 수 있다. 공정하다. **로컬은 제약할 수 있고 API는 할 수 없다는
것이 배포 현실이고, 그 비대칭이 자체 호스팅의 실질 이점이다.**

## 7. 말할 수 있는 것과 없는 것

**말할 수 있다**
- Gemini와의 격차를 judge 총점에서 80% 좁혔고, 오탐은 동률이다
- 겨냥한 축(희소 근거, 인프라 계층)의 데이터가 오탐을 7/18에서 1/18로 내렸다
- 제약 디코딩의 순효과는 모델의 판별력에 달려 있다. 예측하고 실측했다
- 두 시스템은 서로 다른 것을 틀린다. 총점 차이가 능력 차이와 같지 않다

**말할 수 없다**
- 대조 쌍이 효과가 있었다 — v3 대비 1건씩 차이, p = 0.75
- v6c가 Gemini에 근접한 것이 학습만의 성과다 — 0.906까지가 학습, 나머지가 디코더
- 대조 쌍과 함정의 개별 기여 — 같은 팔에 넣어 분리되지 않음
