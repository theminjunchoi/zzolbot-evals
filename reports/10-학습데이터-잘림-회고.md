# 학습 데이터 70%가 잘린 채로 학습된 건

## 무엇이 일어났나

SFT 1차(`sft-v1`)를 학습하고 평가해 인용 검증 통과율이 3/15에서 7/15로 올랐다고 기록했다.
효과가 학습 실행에 견고한지 확인하려고 **시드만 바꿔 같은 데이터로 재학습**했더니 결과가 무너졌다.

| | 인용 검증 통과 | JSON 파싱 실패 |
|---|---|---|
| 베이스 | 3/15 | 0 |
| 시드 1 | 7/15 | 0 |
| **시드 2** | **2/15** | **2** |

두 학습의 loss는 거의 같았다(val 0.539 대 0.558). 그런데 행동은 완전히 달랐고, 시드 2는
베이스에는 없던 JSON 파싱 실패까지 냈다.

## 원인

두 번째 학습에서는 로그를 파일로 남겼고, 거기 경고가 있었다.

```
Some sequences are longer than 2048 tokens.
The longest sentence 2235 will be truncated to 2048.
```

토큰 길이를 직접 재보니 이랬다.

| | 중앙 | 최대 |
|---|---|---|
| 학습 샘플 전체 | 2235 | 3086 |
| 그중 정답(assistant) | 374 | 503 |
| 평가 시나리오 입력 | 1254 | 2573 |

**100건 중 70건이 2048을 넘었다.** 그리고 잘리는 쪽은 뒤쪽, 즉 정답 부분이다.
결정적으로 응답 스키마의 필드 순서가 이렇다.

```json
{"summary": ..., "rootCauseHypothesis": ..., "suggestedActions": [...],
 "evidenceFound": ..., "evidenceLine": "..."}
```

`evidenceLine`이 맨 끝이다. **잘림이 정확히 가르치려던 필드를 지웠다.** 70%의 샘플이
"JSON을 쓰다 마는" 패턴을 가르친 셈이고, 그래서 시드에 따라 어떤 실행은 운좋게 인용을 배우고
어떤 실행은 미완성 JSON을 배웠다. 시드 2의 파싱 실패가 그 결과다.

## 왜 늦게 발견했나

두 가지가 겹쳤다.

**1. 첫 학습에서 로그를 흘렸다.** 백그라운드 전환 과정에서 앞부분이 잘려 나갔고, 초기 val loss와
잘림 경고가 모두 그 안에 있었다. 로그를 파일로 남기는 기본 습관 하나가 두 개의 신호를 가렸다.

**2. 데이터 검증기에 길이 검사가 없었다.** 스키마, 기대 판정, 인용 원문 일치, 근거 없을 때 원인
부재, 식별자 접지까지 다섯 가지를 검사하면서 정작 "**이 샘플이 학습기에 온전히 들어가는가**"는
확인하지 않았다. 데이터 품질 검증에서 가장 기본적인 항목이 빠져 있었다.

## 조치

### 데이터를 깎지 않고 예산을 올린다

세 가지 선택지가 있었다.

| 방안 | 판단 |
|---|---|
| 긴 샘플 탈락 | 100건 중 70건 손실. 선택지가 아니다 |
| 데이터를 짧게 조정 | **평가 시나리오도 최대 2573 토큰이다.** 학습만 짧게 맞추면 짧은 입력으로 배우고 긴 입력으로 시험 보는 상태가 된다. 더 나쁘다 |
| **max_seq_length를 올린다** | 손실 0, 왜곡 0. 채택 |

`max_seq_length`는 물리적 한계가 아니라 임의로 정한 값이었고, 실제 제약인 메모리는
2048에서 18.5GB로 48GB 중 여유가 있었다. 3200으로 올리고 배치를 2에서 1로 낮춰 길이를 확보했다.

### 검사는 필터가 아니라 가드로 만든다

`training/length_guard.py`를 추가했다. 긴 샘플을 **거르지 않는다.** 설정된 최대 길이를 넘는
샘플이 하나라도 있으면 **빌드를 중단하고 설정을 올리라고 알린다.**

```
100건 중 70건이 max_seq_length 2048을 넘는다(최장 3086).
샘플을 버리거나 깎지 말고 --max-seq-length를 3200 이상으로 올려라.
메모리가 모자라면 배치 크기를 줄인다.
```

거르는 필터로 만들었다면 데이터가 조용히 사라지고 같은 사고가 반복된다. 사람이 예산을
조정하도록 강제하는 것이 맞다.

### 재학습 조건

- max_seq_length 3200 (최장 3086을 덮음), batch 1, iters 400
- 로그는 파일로 보존
- 시드 2개로 재현성 확인

## 남는 교훈

**차단기가 값을 했다.** 시드 하나를 바꿔보는 23분짜리 검증이 없었다면, 7/15을 믿고 평가셋
확대에 두 시간을 더 쓴 뒤에도 원인을 몰랐을 것이다. 가장 싼 반증부터 놓는 순서가 옳았다.

**그리고 이 건은 "SFT가 효과 없다"가 아니다.** 결함 있는 데이터로 학습해서 결과를 신뢰할 수
없다는 것이다. 두 진술을 구분하지 않으면 잘못된 결론으로 넘어간다.
