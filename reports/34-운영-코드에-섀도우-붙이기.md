# 34. 운영 코드에 섀도우 붙이기

리포트 31~33번으로 **무엇을 배포할지**는 정해졌다. Q8_0 GGUF에 GBNF 인용 제약을 걸고
llama.cpp로 서빙한다. 남은 질문은 **그것을 실제 운영 코드에 어떻게 끼워 넣느냐**다.

이 리포트는 그 작업의 기록이다. 코드는 zzol 팀 저장소에 있고(PR #1799) 여기에는 결정과
실패만 남긴다.

## 1. 무엇을 만들었나

알림 하나가 들어오면 Gemini와 자체 모델이 **같은 입력으로 나란히 답한다.** 운영 판정과
Slack 게시는 전부 Gemini 것이고, 자체 모델의 답은 테이블에만 쌓인다. 기본값은 꺼짐이다.

```text
Alertmanager firing
  └ ShadowAnomalyAnalyzer (@Primary 데코레이터)
      ├ 권위: Gemini → 인용 검증 → Slack     (동기, 지금과 동일)
      └ 섀도우: llama.cpp → 기록만           (가상 스레드, 응답을 안 기다림)
```

목적은 모델 교체가 아니라 **비교 데이터 수집**이다. 지금까지 잰 것은 전부 내가 만든 합성
시나리오 33종이고, 그건 문제를 낸 사람과 푸는 사람이 같다는 약점이 있다. 실제 알림은 아무도
정답을 미리 만들지 않은 문제다.

## 2. 설계에서 실제로 고민한 것

### 프롬프트를 한 벌로 묶었다

두 모델을 비교하려면 입력과 채점이 같아야 한다. 프롬프트가 두 벌이면 차이가 모델에서 온
것인지 프롬프트에서 온 것인지 가릴 수 없다. 그래서 프롬프트 조립과 인용 검증을 분석기
밖으로 빼서 공유 계약(`MonitorAnalysisContract`, `CitationVerifier`)으로 만들었다.

### 접지 전과 후를 나눠 기록한다

리포트 14번에서 정한 구분을 그대로 스키마에 넣었다. 모델이 "근거 있다"고 주장한 값과, 인용
검증을 통과한 뒤의 값을 각각 저장한다. 하나만 저장하면 나중에 모델의 판별력을 되물을 수 없다.

### 응답을 기다리지 않는다

ARM 2코어에서 알림 한 건이 최장 121초다(리포트 33번). 같은 스레드에서 이어 돌리면 그게
그대로 Slack 게시 지연이 된다. 웹훅 수신기가 쓰는 가상 스레드 풀에 던지고 즉시 반환한다.

### 평가 경로는 섀도우를 안 탄다

데코레이터가 `@Primary`라, 한정자 없이 주입받는 곳은 전부 섀도우를 타게 된다. 박제 시나리오
평가기가 거기 걸리면 **평가 실행이 비교 기록으로 쌓여** 실제 알림과 섞인다. 권위 분석기에
한정자를 붙여 끊었다.

## 3. 내가 낸 사고 두 건

기록하는 이유는 둘 다 **테스트가 아니라 CI가 잡았기** 때문이다.

### (1) 설정 record에 생성자를 하나 더 얹었다

테스트에서 쓰기 편하라고 3인자 편의 생성자를 추가했다. Spring의
`@ConfigurationProperties` record 바인딩은 **비-private 생성자가 정확히 하나**여야 한다.
두 개가 되는 순간 기본 생성자를 찾다가 `NoSuchMethodException`으로 애플리케이션이 아예 안
뜬다. 단위 테스트는 전부 초록이었고 컨텍스트가 뜨는 곳이 없어 아무도 못 잡았다.

되돌리고 `ApplicationContextRunner`로 바인딩 회귀 테스트를 추가했다.

### (2) 프롬프트를 옮기면서 규칙 세 줄을 흘렸다

`SYSTEM_INSTRUCTION`을 공유 계약으로 옮기는 과정에서 원본을 앞부분만 읽고 재구성했다.
규칙 세 개(제안 조치 제약, 시간 정합성, 양적 정합성)가 사라졌다. 하필 **골든셋의
`stale-reingested-v2`와 `sparse-two-lines`가 정확히 그 규칙에 걸려 있다.** 리포트 18번과
29번에서 만든 시나리오들이다.

`git show origin/dev`로 원문을 뽑아 바이트 단위로 같은지 확인하고 되돌렸다.

두 사고 모두 **"옮기기만 했다"고 생각한 변경**에서 나왔다. 옮긴 것은 바이트로 비교하는 게
맞다.

## 4. 리포트 33번이 코드에 요구한 것

측정이 끝난 뒤 기본값 두 개를 고쳤다.

| 항목 | 처음 | 고친 값 | 이유 |
|---|---|---|---|
| 읽기 타임아웃 | 120초 | 240초 | 2코어 최장이 121초다. 120초는 긴 알림에서 거의 매번 잘린다 |
| 토큰 상한 키 | `n_predict` | `n_predict` + `max_tokens` | 지금 서버는 둘 다 받는다. 버전이 올라 한쪽만 남으면 생성이 안 끊긴다 |

타임아웃을 실측 전에 정했으면 첫 배포에서 전부 타임아웃으로 기록됐을 것이다. 순서가
운이 좋았던 게 아니라, 재고 나서 쓰기로 한 결과다.

## 5. 남은 것

- **배포.** llama-server를 운영 compose에 `--cpus 2`로 올리고 모델을 볼륨 마운트한다.
  앱 컨테이너에서 보는 주소는 `127.0.0.1`이 아니다.
- **데이터 축적.** 비교 행이 모이기 전에는 아무 말도 할 수 없다.
- **권위 쪽 인용 원문.** `MonitorAnalysis`에 인용 필드가 없어 Gemini가 어느 줄을 근거로
  삼았는지는 안 남는다. 판정 비교는 되고 인용 비교는 자체 모델 쪽만 된다.

## 6. 다음 리포트에서 답할 질문

실제 알림에서 두 모델의 판정이 얼마나 갈리는가. 그리고 갈릴 때 **누가 맞는가.**
합성 33종에서는 두 시스템이 서로 다른 것을 틀렸다(리포트 15번). 실전에서도 그런지가 관심사다.
