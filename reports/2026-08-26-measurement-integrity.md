# 측정 신뢰도 점검 (시니어 점검 지적 4건 처리)

확장 29종 측정 직후, 측정기 자체의 신뢰도가 작업 속도를 따라오지 못한다는 판단으로
규모 확장을 미루고 아래 4건을 먼저 처리했다.

## 1. 평가 경로와 합성 경로의 샘플링 분리 (버그 수정)

`GeminiJsonClient`가 분석기 계약(temperature 0, topP 0)을 하드코딩했는데 합성 생성기도 같은
클라이언트를 썼다. 결정적 디코딩이라 같은 프롬프트에 같은 출력이 나왔고, 실제로 파일럿에서
초 단위 타임스탬프까지 동일한 복제 시나리오(spike-16/17)가 생산됐다. 우연이 아니라 설계 귀결이었다.

- 조치: 샘플링 파라미터를 생성자 인자로 분리. 평가 경로는 0 유지, 합성 경로는 temperature 0.9,
  topP 0.95. topP를 함께 올린 이유는 temperature만 올리고 topP를 0으로 두면 여전히 greedy에
  가깝기 때문이다.
- 회귀 방지: `tests/test_sampling_contract.py`가 두 경로의 기본값이 분리돼 있음을 고정한다.

## 2. outbox-33 실패의 안정성 확인

"포화가 깨졌다"는 선언이 단일 시행 결과에 얹혀 있었다. judge 판정이 같은 답변에 3→5→3으로
출렁인 전례가 있어 노이즈 가능성을 배제해야 했다.

- 결과: **5시행 5/5 FAIL.** 실패 메커니즘도 매번 동일하게 재현됐다. 봇이 '근거 발견: 예'로
  판정하고 정산 스트림 소비 실패를 Outbox DEAD_LETTER 적체의 원인으로 지목한다.
- 판정: judge 노이즈가 아니라 안정적인 모델 실패. 다음 개선 실험의 표적으로 삼는 것이 정당하다.
- 실패의 성격: 발행 측(OutboxEventProcessor 재시도 소진)과 소비 측(정산 컨슈머 실패)은 서로
  다른 메커니즘인데 봇이 둘을 인과로 연결한다. 도메인 구조 지식이 필요한 실패다.

## 3. judge 변별력 캘리브레이션

축적된 실측 판정 89건이 87 PASS / 2 FAIL로 쏠려 있어, judge가 오답을 잡아내는 능력을 잴 표본이
없었다. 사람이 89건을 라벨링하는 대신, **정답 답변을 규칙 위반 방향으로 변형한 프로브**로 쟀다.
참조 라벨이 "누가 읽고 매긴 의견"이 아니라 "어떻게 만들었는가"에서 나오므로 라벨링 주관을 우회한다.

변형 5종: 원본 유지(대조군, PASS 기대), 판정 뒤집기(FAIL), 원인 날조(FAIL), 컴포넌트 바꿔치기(FAIL),
무해한 말바꾸기(대조군, PASS 기대).

- 결과: **40/40 (100%)**. 놓친 오답 0건, 과잉 탈락 0건.

| 변형 | 참조 라벨 | 일치율 |
|---|---|---|
| unmutated | PASS | 10/10 |
| benign-paraphrase | PASS | 10/10 |
| verdict-flip | FAIL | 10/10 |
| fabricated-cause | FAIL | 5/5 |
| component-swap | FAIL | 5/5 |

**해석의 한계(중요)**: 이 프로브들은 명백한 오답이다. judge가 총체적 오류를 100% 잡는다는 것은
확인했지만, 우리가 실제로 관찰한 판정 변동은 "정답인데 원인 가설 표현이 약간 부족한" 경계
영역에서 나왔고 이 셋은 그 영역을 재지 못한다. 즉 이번 측정은 judge의 하한을 보장할 뿐
정밀도를 보장하지 않는다. v2 프로브(원인을 부분적으로만 맞히기, 표현을 애매하게 흐리기,
근거 인용은 맞고 해석만 빗나가기)가 다음 과제다.

## 4. dev/test 분할 도입

시간/양 접지 규칙은 FAIL 2건을 보고 만들어 같은 셋에서 20/20을 확인했다. 한 번은 정당한
오답노트 루프지만, 이 패턴을 반복하면 개선인지 평가셋 암기인지 구별할 수 없어진다.

- `golden-set/splits.json`으로 분할을 명시하고 `--split dev|test|all`로 거른다.
- 현재 배정: **dev 21종, test 8종.**
  - dev: 원본 20종(프롬프트 튜닝에 이미 사용되어 오염됨) + outbox-33(다음 실험의 표적)
  - test: 나머지 합성 승격분 8종(튜닝에 한 번도 사용되지 않음)
- 규칙: 개선 실험은 dev만 보고, 최종 보고 숫자는 test에서 낸다. 새로 합성한 시나리오는 튜닝
  표적으로 쓰지 않는 한 test로 보내 test를 키운다.
- 한계: test n=8은 작아서 오차 막대가 넓다. 100+ 확장의 최우선 목적은 test 규모 확보다.
- 회귀 방지: `tests/test_splits.py`가 모든 시나리오가 정확히 한 분할에 속함을 고정한다.
