# 23. 어댑터 팔 엔진 대조

> **사전 등록 절(1~4)은 결과를 보기 전에 쓰고 커밋했다.** 결과 절은 측정이 끝난 뒤
> 채운다. 결과를 보고 기준을 옮기는 것을 막기 위해 순서를 이렇게 한다.

리포트 22번에서 **베이스 모델**의 엔진 대조를 끝냈다(33종 중 31종 일치, 2종은 bf16
1 ULP 타이). 어댑터를 얹은 팔은 안 쟀고, 그것이 계획 1번의 남은 절반이다.

## 1. 무엇을 묻는가

**같은 베이스에 같은 어댑터를 얹었을 때 두 엔진이 같은 답을 내는가.**

각자 학습한 어댑터끼리 비교하면 차이가 학습에서 왔는지 추론에서 왔는지 못 가른다.
그래서 **어댑터를 하나로 고정**한다. MLX가 학습한 `sft-v6-s1`을 peft 형식으로 변환해
양쪽에 얹는다.

이 어댑터는 4bit 베이스에서 학습됐고 여기서는 bf16 베이스에 얹는다. **의미 있는 모델이
아니다.** 하지만 베이스와 어댑터가 양쪽에서 동일하므로 엔진 대조로는 정당하다.
묻는 것은 "이 모델이 좋은가"가 아니라 "두 엔진이 같은 것을 계산하는가"다.

## 2. 변환에서 맞춰야 했던 것

추측했으면 전부 틀렸을 값들이라 **mlx-lm 소스와 학습된 어댑터 파일을 직접 읽었다.**

| 항목 | 실측값 | 처음에 쓰려던 값 |
|---|---|---|
| 대상 모듈 | **7종** (q, k, v, o, gate, up, down) | q, v 2종 |
| 레이어 | 12~27 (뒤 16개) | 같음 |
| rank | 8 | 8 |
| scale | **20.0** → peft `lora_alpha=160` | alpha 16 (스케일 **2.0**) |
| 옵티마이저 | **adam** | AdamW |
| 텐서 수 | 224 | 32 |

두 가지가 위험했다.

**하나. mlx-lm의 기본 `keys`는 q_proj/v_proj가 아니다.** `get_keys_for_lora`가 디코더
레이어 안의 **모든 `nn.Linear`**를 모은다. 관행적으로 q/v만 건다고 알려져 있어 그렇게
가정하기 쉽다.

**둘. 스케일 규약이 다르다.**

```
mlx   lora_a [in, r]   lora_b [r, out]   y += scale * (x @ lora_a @ lora_b)
peft  lora_A [r, in]   lora_B [out, r]   y += (alpha/r) * lora_B(lora_A(x))
```

`lora_A = lora_a.T`, `lora_B = lora_b.T`, `alpha = scale * r`이다. **alpha에 scale을
그대로(20) 넣으면 어댑터 효과가 8분의 1로 걸린다.** 출력이 그럴듯하게 나오므로 조용히
틀린다. 그래서 델타가 같은지를 단위 테스트로 못박았다.

## 3. 버린 시험: 무작위 어댑터

90분짜리 학습을 걸기 전에 **가장 싼 반증**을 놓으려고 무작위 LoRA로 로짓을 맞댔다.
결과가 최대 절대차 **7.06**(ULP의 100배 이상)이었다.

**이건 버그가 아니라 시험 설계 문제였다.** 표준편차 0.02에 스케일 20을 곱해 112개
모듈에 걸면 모델이 정상 작동 범위 밖으로 밀려난다. 거기서는 미세한 수치 차이가 16개
레이어를 지나며 폭발한다. 학습된 어댑터는 `lora_b`가 0에서 출발해 작게 자라므로 성격이
완전히 다르다.

실제 `sft-v6-s1`로 바꿔 단일 프롬프트를 재니 이렇게 나왔다.

```
로짓 최대 절대차 0.26562   (bf16 ULP 0.125의 2.1배)
중앙값           0.03125   (ULP 이하)
argmax 일치 True,  상위 5개 일치 True
mlx lora dtype float32, peft lora dtype float32, 스케일 양쪽 20.0
```

**교훈**: 대리 입력으로 도구를 시험할 때는 **그 대리가 실제 입력과 같은 분포에 있는지**
부터 확인해야 한다. 오탐이 났고, 이걸 버그로 읽고 변환기를 뜯었다면 멀쩡한 코드를
망가뜨렸을 것이다. 평가셋을 만들 때 늘 신경 쓰는 문제인데 도구 시험에서는 놓쳤다.

## 4. 사전 등록한 판정 기준

리포트 22번에서 세운 것을 쓰되, **어댑터 팔은 허용 폭을 넓힌다.**

| 불일치 | 처리 |
|---|---|
| 0종 | 성공 |
| 1~5종 | **개별로 첫 분기 지점의 로짓 간격을 확인해야** 성공. 자동 통과 금지 |
| 6종 이상 | 설정 불일치가 남아 있다. 실패 |

**베이스(1~2종)보다 넓힌 이유를 먼저 적는다.** 어댑터 가중치가 fp32이고 베이스가
bf16이라 누적 경로가 하나 더 늘어난다. 실제로 단일 프롬프트 최대차가 베이스보다 컸다
(ULP의 2.1배). 그리디에서는 분기 하나가 뒤 문장 전체를 갈라놓으므로 건수가 늘어난다.

**결과 보기 전 예측**: 불일치 **2~5종**. 판정은 성공. 전부 타이로 설명될 것으로 본다.

`k`(같은 것을 두 번 재는 변동)는 이번에도 못 잰다. 그리디는 결정적이라 시드가 아무것도
바꾸지 않는다. 리포트 22번 5절에 같은 한계를 적었다.

## 5. 결과: 불일치 4종, 전부 수치적으로 미결정된 자리

| 팔 | 보상 | 인용 | 오탐 | 파싱 실패 |
|---|---|---|---|---|
| MLX + sft-v6-s1 | 0.903 | 13/15 | 4/18 | 0 |
| torch + 같은 어댑터(변환) | 0.858 | 11/15 | 5/18 | 0 |

**불일치 4종 / 33종.** 사전 등록한 1~5종 구간이라 개별 확인 대상이다.

| 시나리오 | MLX | torch | 갈린 항목 |
|---|---|---|---|
| error-budget-burn-slow-11 | 1.00 | 0.50 | 판정 |
| 5xx-redis-connection-failure | 1.00 | 0.60 | 인용 |
| error-spike-roomjoin-current-window | 1.00 | 0.60 | 인용 |
| app-error-log-spike-19 | 0.70 | 0.50 | 감점 |

어댑터는 확실히 걸렸다. 같은 베이스에서 인용이 2/15에서 13/15로 갔다.

### 첫 분기 지점의 로짓 간격

네 건 모두 **1~2등 간격이 0~2 ULP**다(bf16 ULP는 이 크기대에서 0.125).

| 시나리오 | 첫 분기 | MLX 간격 | torch 간격 | 두 엔진 로짓 최대차 |
|---|---|---|---|---|
| error-budget-burn-slow-11 | 15 | 1.0 ULP | **0.0 ULP** | 0.391 |
| 5xx-redis-connection-failure | 115 | 2.0 ULP | 1.0 ULP | 0.438 |
| error-spike-roomjoin | 10 | 1.0 ULP | 1.0 ULP | 0.281 |
| app-error-log-spike-19 | 10 | 2.0 ULP | 2.0 ULP | 0.344 |

### 진단 도구를 두 번 고쳤다. 그쪽이 더 값나간다

**1차 시도가 모순을 냈다.** 두 시나리오에서 "그리디인데 2등을 골랐다"가 나왔다.
그리디에서 2등을 고를 수는 없으므로 측정이 틀린 것이다.

**원인 1: 재토큰화.** 저장된 **텍스트**를 다시 토큰화해 분기 위치를 찾았다.
`decode -> encode` 왕복은 보장되지 않아 경계가 실제 생성과 어긋난다. 생성 루프에서
토큰 id를 직접 받도록 고쳤다(mlx는 `stream_generate`, torch는 `generate`의 반환값).

**원인 2: 이쪽이 진짜다.** 고친 뒤에도 두 건에서 모순이 남았다. 남은 설명은
**검증은 전체 시퀀스를 한 번에 forward 하는데 실제 생성은 KV 캐시로 증분 계산한다**는
것뿐이었다. 축약 순서가 달라 로짓 하위 자리가 갈린다.

같은 엔진 안에서 확인했다. 가중치도 그리디 설정도 같고 **캐시만 껐다.**

```
torch, use_cache=True   -> 10번째 토큰 ' ERROR'
torch, use_cache=False  -> 10번째 토큰 ' 방'     <- MLX와 같은 선택
```

**엔진 간 차이가 아니라 한 엔진 안에서 계산 경로가 둘이라 갈린 것이다.**
1~2 ULP 간격에서는 캐시 유무만으로 argmax가 뒤집힌다.

**판정: 성공.** 네 자리 모두 두 엔진이 **구별할 수 없는 값**을 보고 있고, 같은 엔진조차
경로에 따라 다르게 답한다. 계산의 차이가 아니다.

**예측은 맞았다.** 2~5종을 예상했고 4종이 나왔으며 전부 타이로 설명됐다.

### 설명하지 못한 것 하나

**네 건 모두 torch가 낮다**(-0.50, -0.40, -0.40, -0.20). 무작위 타이라면 방향이
섞여야 한다. 베이스 대조(리포트 22번)에서는 -0.40과 +0.20으로 갈렸다.

동전 던지기라면 네 번 같은 방향이 나올 확률은 12.5%라 이 자체로는 이상하다고 못 한다.
**그러나 n=4로는 방향 편향을 배제할 수도 없다.** 평가셋이 116종으로 늘면 같은 대조를
다시 걸어 방향 분포를 봐야 한다. 지금 결론 내리지 않고 열어 둔다.

## 6. 말할 수 있는 것과 없는 것

**말할 수 있다**
- **같은 베이스에 같은 어댑터를 얹으면 두 엔진이 같은 것을 계산한다.** 33종 중 29종
  완전 일치, 4종은 0~2 ULP 자리의 갈림
- mlx 어댑터를 peft로 옮기는 규약을 실측으로 확정했다. 전치 두 번과 `alpha = scale * r`
- **1~2 ULP 간격에서는 KV 캐시 유무만으로 그리디 선택이 뒤집힌다.** 같은 엔진 안에서
  실측했다. 이 수준의 불일치는 엔진 대조의 판정 근거가 될 수 없다
- 어댑터 적용 경로가 정상이다. 인용 2/15 -> 13/15

**말할 수 없다**
- **학습까지 재현된다** - 어댑터는 MLX가 학습한 하나뿐이다. 아래에 이어 적는다
- **torch가 MLX보다 나쁘다** - 평균 차이 0.045는 전부 타이 4종에서 나온다.
  다만 방향이 한쪽으로 몰린 것은 설명하지 못했다(n=4)
- **이 팔의 성능 수치에 의미가 있다** - 4bit에서 학습한 어댑터를 bf16 베이스에 얹은
  조합이라 의미 있는 모델이 아니다. 엔진 대조용으로만 쓴다
- 4bit 어댑터가 bf16 베이스에서도 통한다 - 보상 0.906 대 0.903으로 비슷해 보이나
  구성이 다르다(인용 9/15 대 13/15, 오탐 1/18 대 4/18). 축이 둘이라 비교 불가

**미리 못박아 두는 범위**: 이 대조가 성공해도 **"학습까지 재현된다"는 말할 수 없다.**
어댑터는 MLX가 학습한 하나뿐이고, torch로 학습해 같은 곳에 도달하는지는 다른 질문이다.

그리고 그 학습 대조는 **완전 일치를 기대할 수 없는 축**이다.

- LoRA 초기화가 다르다. mlx는 `lora_a`를 `uniform(-1/sqrt(in), 1/sqrt(in))`로 채우고
  peft는 kaiming을 쓴다. 난수 생성기도 달라 시드를 맞춰도 같은 초기값이 안 나온다
- 옵티마이저 기본값이 다르다(mlx `adam` 대 peft 예제의 AdamW)

따라서 학습 대조의 판정 기준은 **"같은 어댑터가 나오는가"가 아니라 "같은 종점에
도달하는가"**여야 한다. 그러려면 **한쪽에서 시드를 여러 개 돌려 종점의 변동 폭부터
재야 한다.** 리포트 12번에서 이미 겪었다. 거기서 종점 두 개는 일치하는데 시나리오별
판정은 27/33만 일치했다.
