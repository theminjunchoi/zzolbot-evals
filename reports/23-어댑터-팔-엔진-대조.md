# 23. 어댑터 팔 엔진 대조

> **사전 등록 절(1~4)은 결과를 보기 전에 쓰고 커밋했다.** 결과 절은 측정이 끝난 뒤
> 채운다. 결과를 보고 기준을 옮기는 것을 막기 위해 순서를 이렇게 한다.

리포트 22번에서 **베이스 모델**의 엔진 대조를 끝냈다(33종 중 31종 일치, 2종은 bf16
1 ULP 타이). 어댑터를 얹은 팔은 안 쟀고, 그것이 계획 1번의 남은 절반이다.

## 1. 무엇을 묻는가

**같은 베이스에 같은 어댑터를 얹었을 때 두 엔진이 같은 답을 내는가.**

각자 학습한 어댑터끼리 비교하면 차이가 학습에서 왔는지 추론에서 왔는지 못 가른다.
그래서 **어댑터를 하나로 고정**한다. MLX가 학습한 `sft-v6-s1`을 peft 형식으로 변환해
양쪽에 얹는다.

이 어댑터는 4bit 베이스에서 학습됐고 여기서는 bf16 베이스에 얹는다. **의미 있는 모델이
아니다.** 하지만 베이스와 어댑터가 양쪽에서 동일하므로 엔진 대조로는 정당하다.
묻는 것은 "이 모델이 좋은가"가 아니라 "두 엔진이 같은 것을 계산하는가"다.

## 2. 변환에서 맞춰야 했던 것

추측했으면 전부 틀렸을 값들이라 **mlx-lm 소스와 학습된 어댑터 파일을 직접 읽었다.**

| 항목 | 실측값 | 처음에 쓰려던 값 |
|---|---|---|
| 대상 모듈 | **7종** (q, k, v, o, gate, up, down) | q, v 2종 |
| 레이어 | 12~27 (뒤 16개) | 같음 |
| rank | 8 | 8 |
| scale | **20.0** → peft `lora_alpha=160` | alpha 16 (스케일 **2.0**) |
| 옵티마이저 | **adam** | AdamW |
| 텐서 수 | 224 | 32 |

두 가지가 위험했다.

**하나. mlx-lm의 기본 `keys`는 q_proj/v_proj가 아니다.** `get_keys_for_lora`가 디코더
레이어 안의 **모든 `nn.Linear`**를 모은다. 관행적으로 q/v만 건다고 알려져 있어 그렇게
가정하기 쉽다.

**둘. 스케일 규약이 다르다.**

```
mlx   lora_a [in, r]   lora_b [r, out]   y += scale * (x @ lora_a @ lora_b)
peft  lora_A [r, in]   lora_B [out, r]   y += (alpha/r) * lora_B(lora_A(x))
```

`lora_A = lora_a.T`, `lora_B = lora_b.T`, `alpha = scale * r`이다. **alpha에 scale을
그대로(20) 넣으면 어댑터 효과가 8분의 1로 걸린다.** 출력이 그럴듯하게 나오므로 조용히
틀린다. 그래서 델타가 같은지를 단위 테스트로 못박았다.

## 3. 버린 시험: 무작위 어댑터

90분짜리 학습을 걸기 전에 **가장 싼 반증**을 놓으려고 무작위 LoRA로 로짓을 맞댔다.
결과가 최대 절대차 **7.06**(ULP의 100배 이상)이었다.

**이건 버그가 아니라 시험 설계 문제였다.** 표준편차 0.02에 스케일 20을 곱해 112개
모듈에 걸면 모델이 정상 작동 범위 밖으로 밀려난다. 거기서는 미세한 수치 차이가 16개
레이어를 지나며 폭발한다. 학습된 어댑터는 `lora_b`가 0에서 출발해 작게 자라므로 성격이
완전히 다르다.

실제 `sft-v6-s1`로 바꿔 단일 프롬프트를 재니 이렇게 나왔다.

```
로짓 최대 절대차 0.26562   (bf16 ULP 0.125의 2.1배)
중앙값           0.03125   (ULP 이하)
argmax 일치 True,  상위 5개 일치 True
mlx lora dtype float32, peft lora dtype float32, 스케일 양쪽 20.0
```

**교훈**: 대리 입력으로 도구를 시험할 때는 **그 대리가 실제 입력과 같은 분포에 있는지**
부터 확인해야 한다. 오탐이 났고, 이걸 버그로 읽고 변환기를 뜯었다면 멀쩡한 코드를
망가뜨렸을 것이다. 평가셋을 만들 때 늘 신경 쓰는 문제인데 도구 시험에서는 놓쳤다.

## 4. 사전 등록한 판정 기준

리포트 22번에서 세운 것을 쓰되, **어댑터 팔은 허용 폭을 넓힌다.**

| 불일치 | 처리 |
|---|---|
| 0종 | 성공 |
| 1~5종 | **개별로 첫 분기 지점의 로짓 간격을 확인해야** 성공. 자동 통과 금지 |
| 6종 이상 | 설정 불일치가 남아 있다. 실패 |

**베이스(1~2종)보다 넓힌 이유를 먼저 적는다.** 어댑터 가중치가 fp32이고 베이스가
bf16이라 누적 경로가 하나 더 늘어난다. 실제로 단일 프롬프트 최대차가 베이스보다 컸다
(ULP의 2.1배). 그리디에서는 분기 하나가 뒤 문장 전체를 갈라놓으므로 건수가 늘어난다.

**결과 보기 전 예측**: 불일치 **2~5종**. 판정은 성공. 전부 타이로 설명될 것으로 본다.

`k`(같은 것을 두 번 재는 변동)는 이번에도 못 잰다. 그리디는 결정적이라 시드가 아무것도
바꾸지 않는다. 리포트 22번 5절에 같은 한계를 적었다.

## 6. 말할 수 있는 것과 없는 것

(측정 후)

**미리 못박아 두는 범위**: 이 대조가 성공해도 **"학습까지 재현된다"는 말할 수 없다.**
어댑터는 MLX가 학습한 하나뿐이고, torch로 학습해 같은 곳에 도달하는지는 다른 질문이다.

그리고 그 학습 대조는 **완전 일치를 기대할 수 없는 축**이다.

- LoRA 초기화가 다르다. mlx는 `lora_a`를 `uniform(-1/sqrt(in), 1/sqrt(in))`로 채우고
  peft는 kaiming을 쓴다. 난수 생성기도 달라 시드를 맞춰도 같은 초기값이 안 나온다
- 옵티마이저 기본값이 다르다(mlx `adam` 대 peft 예제의 AdamW)

따라서 학습 대조의 판정 기준은 **"같은 어댑터가 나오는가"가 아니라 "같은 종점에
도달하는가"**여야 한다. 그러려면 **한쪽에서 시드를 여러 개 돌려 종점의 변동 폭부터
재야 한다.** 리포트 12번에서 이미 겪었다. 거기서 종점 두 개는 일치하는데 시나리오별
판정은 27/33만 일치했다.
