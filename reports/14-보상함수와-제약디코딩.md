# 검증 가능한 보상과 제약 디코딩

사전 등록한 학습 계획([13번](13-사전등록-학습-계획.md))의 A단계와 C단계 일부를 실행한 기록이다.
가장 값진 결과는 학습 쪽이 아니라 **운영 시스템의 방어 하나가 우연에 기대고 있었다는 발견**이다.

## 1. 보상 함수: 하나가 세 역할을 한다

| 역할 | 쓰임 |
|---|---|
| 학습 신호 | RFT가 샘플을 고르는 기준, DPO가 선호 쌍을 만드는 기준 |
| 평가 종점 | judge를 안 부르므로 API 비용 0, 채점 변동 미포함 |
| 판정 기준 | 사전 등록한 성공 조건을 이 값으로 판정 |

배점은 이렇다. 만점 1.0.

| 항목 | 배점 | 라벨 필요 |
|---|---|---|
| 형식 유효 (JSON 파싱 + 필드) | 0.10 | 불필요 |
| 판정 일치 (`evidenceFound` == 기대) | 0.50 | **필요** |
| 인용 원문 일치 (로그 한 줄 전체) | 0.40 | 불필요 |
| 근거 없는데 원인을 말함 | -0.30 | 불필요 |

**근거 없음이 정답인 시나리오에서는 인용을 만점 처리한다.** 그러지 않으면 음성의 상한이
0.6이 되어 양성과 척도가 어긋나고, 음성만 잘하는 모델이 낮게 나온다.

### 왜 이진 PASS가 아니라 연속값인가

33종에서 이진으로 세면 검정력이 없다.

```
개선 3 / 악화 0 → p = 0.2500   완벽해도 유의하지 않음
개선 6 / 악화 0 → p = 0.0312
```

연속값이면 짝지은 비모수 검정을 쓸 수 있고, 중간 크기 효과(d=0.5)는 34쌍이면 잡힌다.
**평가셋을 늘리지 않고 검정력을 얻는 방법이 종점을 바꾸는 것이었다.**

### 뺀 항목: 원인 구체성

"원인 가설이 인용한 로그 줄의 컴포넌트를 이름으로 지목해야 한다"는 규칙을 만들고,
배점에 넣기 전에 judge 판정과의 일치율을 쟀다. **사전 등록한 기준은 60% 이상이었다.**

**실측 38%.** 어긋난 131건 중 **123건이 규칙이 더 엄격한** 방향이었다.

```
원인: "Oracle Object Storage 서비스와의 통신 문제로 읽기 시간 초과"   → judge 통과
로그의 이름들: OracleObjectStorageService, QrCodeService             → 규칙 탈락
```

judge는 클래스 이름이 아니라 **메커니즘을 한국어로 짚어도** 구체적이라고 본다. 타당한 서술인데
이름 일치를 요구해 떨어뜨린 것이다. **조작적 정의가 틀렸다.**

같은 데이터에 맞춰 규칙을 고치면 맞추기가 되므로 하지 않았다. 배점에서 빼고 규칙은
진단용으로 남겼다. 다시 설계할 때는 이 데이터가 아닌 곳에서 검증한다.

## 2. 헤드룸 게이트: 통과했으나 성격이 유형마다 다르다

```
v4 그리디 0.788  →  best-of-8 0.958   여유 +0.170   (사전 등록 기준 +0.05)
```

**상한 추정 자체에 분산이 있다.** 같은 조건으로 한 번 더 뽑으니 0.985가 나왔다(여유 +0.197).
샘플링이 확률적이니 당연하지만, **BoN 값을 소수점 셋째 자리까지 인용하면 안 된다**는 뜻이다.
게이트 판정(기준 +0.05)에는 영향이 없다.

**여기서 멈추고 "모델은 이미 답을 안다"고 결론 내릴 뻔했다.** 8개 샘플 중 몇 개가
판정을 맞혔는지 세어보니 하나의 답이 아니었다.

| 유형 | 건수 | 판정 정답 | 만점 | 해석 |
|---|---|---|---|---|
| 전사 오류 | 3 | **7~8/8** | 1~3/8 | 판정은 확실히 안다. 인용만 흔들림 |
| 파싱 예외 | 1 | 7/8 | 6/8 | 형식만 가끔 깨짐 |
| 근거 미주장 | 2 | 4~5/8 | 3~4/8 | 사실상 무작위 |
| 오탐 | 3 | **0~3/8** | 0~2/8 | 틀리는 쪽을 일관되게 선호 |

`http-5xx-ratio-high-sparse-logs`는 **8번 다 틀린다.** 고를 만점 샘플이 없으니
rejection sampling이 손댈 수 없다.

### BoN 상한은 신탁 값이다

보상의 절반(판정 0.5)이 정답 라벨과 비교하는 항목이다. 즉 0.958은
**"어느 샘플이 맞는지 알려주는 신탁이 있다면"**의 값이고 추론 시점에 도달 가능한 성능이 아니다.

그래서 **라벨이 필요한 항목과 아닌 항목을 나눠야 한다.**

- **형식과 인용에서 얻은 여유는 배포 가능하다.** 라벨 없이 고를 수 있다
- **판정에서 얻은 여유는 상한 추정일 뿐이다.** 판정이 4/8로 흔들리면 그 "최고 샘플"은 우연이다

### 철회한 규칙

측정 직후 "만점 샘플이 6개 이상인 프롬프트만 학습에 쓴다"는 규칙을 세웠다가 철회했다.
전사 오류 3건의 만점이 1/8, 2/8, 3/8이므로 **그 규칙은 RFT가 고쳐야 할 것을 정확히 배제한다.**
rejection sampling의 목적이 드물게 맞는 행동을 흔하게 만드는 것인데 정반대로 건 셈이다.

## 3. 제약 디코딩: 전사 오류를 학습 없이 없앴다

인용 실패의 정체가 판단이 아니라 **전사 오류**였다. 옳은 줄을 고르고 글자를 틀린다.

```
모델 인용: [2026-08-26 14:10:05.122] [ERROR] [,] --- [pool-1-thread-4] c.g.h.RedisStreamContainerReco...
실제 원문: [2026-08-26 14:10:05.130] [ERROR] [,] --- [pool-1-thread-4] c.g.h.RedisStreamContainerReco...
                          ^^^ 8밀리초.  유사도 99%
```

`"evidenceLine": "` 이후 다음 토큰을 **허용된 로그 줄들의 토큰 트라이**로 제한했다
(`harness/constrained.py`). 줄 하나를 끝까지 쓰면 닫는 따옴표만 허용한다.
어휘 전체를 훑지 않고 로그 줄 몇 개만 한 번 토큰화하므로 비용이 없다.

| 팔 | 보상 평균 | 인용 통과 | 오탐(접지 후) |
|---|---|---|---|
| v4 그리디 | 0.788 | 10/15 | 3/18 |
| **v4 + 제약** | **0.824** | **13/15** | **7/18** |

**인용이 10/15에서 13/15로 올랐다. 전사 오류 3건이 정확히 회수됐다. 학습이 없었다.**

### 구현 중 잡은 버그

첫 시도에서 제약이 전혀 걸리지 않았다. 출력이 제약 없을 때와 완전히 같았다.

프로세서 호출 횟수와 제약 적용 횟수를 따로 세어 원인을 좁혔다. **201회 호출, 0회 적용.**
mlx는 프로세서에 **프롬프트를 뺀 생성 토큰만** 넘긴다. 프롬프트 길이만큼 잘라내는 코드를
넣어 항상 빈 문자열이 됐다.

출력만 봤으면 "제약 디코딩은 효과가 없다"는 틀린 결론을 냈을 것이다.

## 4. 진짜 발견: 접지 검증이 오탐을 우연히 막고 있었다

제약을 걸자 **오탐이 3/18에서 7/18로 늘었다.**

이걸 처음엔 부작용이라고만 봤는데 그게 아니다.

`citedInLogs`(운영 코드의 접지 검증)는 **날조된 인용**을 잡으려고 만든 것이다.
그런데 실제로는 **오탐까지 막고 있었다.** 무관한 로그를 근거라고 주장하는 모델이
인용도 어설프게 하니, 인용 검증에 걸려 강등된 것이다.

> **모델이 인용을 잘할수록 이 방어가 약해진다.**

증거가 이미 있다. **Gemini는 인용이 15/15로 완벽하다.** 그리고 Gemini가 틀리는 세 종 중
`outbox-dead-letter-high-33`이 정확히 "무관한 정산 로그를 정확히 인용하며 근거라고 주장"하는
경우다. **코드가 못 잡는다.**

이건 우리 모델 얘기가 아니라 **운영 중인 zzolbot의 설계 문제다.**
접지 파이프라인에 **존재 검사**는 있고 **관련성 검사**가 없다.

### 그래서 우리 수치도 다시 읽어야 한다

| 정의 | v4 오탐 | 무엇을 재는가 |
|---|---|---|
| 접지 후 (`grounded`) | 3/18 | **봇의 실제 동작** |
| 원 주장 (`evidenceFound`) | 7/18 | **모델의 판별력** |

둘 다 맞고 질문이 다르다. 봇 동작을 서술할 때는 3/18이 옳다.
다만 **모델의 판별력은 늘 7/18이었고 3/18은 인용 실패가 가려준 값**이다.

**판별 문제는 5건이 아니라 9건 규모다.**

## 5. 이 단계에서 잡은 자기 오류 다섯 개

전부 결과를 기록하기 전에 잡혔고, 잡힌 방법이 같다. **이미 있는 수치와 대조했다.**

| # | 오류 | 어떻게 잡혔나 |
|---|---|---|
| 1 | 구체성 규칙의 조작적 정의 | 사전 등록한 일치율 검사에서 38% |
| 2 | 새 CLI가 `extract_json`을 안 거침 | base 파싱 실패가 18/33인데 과거엔 0건 |
| 3 | 오탐 정의가 기존 리포트와 다름 | 네 팔의 수치가 과거와 안 맞음 |
| 4 | 점수 0.5를 판정 정답으로 셈 | 점수 조합을 실제로 출력해 임계값 확인 |
| 5 | RFT 샘플링 대상이 학습 데이터와 77% 겹침 | 학습 프롬프트 평균(0.871)이 평가셋(0.788)보다 높은 게 이상해서 |

2번과 3번은 **과거 측정을 보존해둔 덕에** 잡혔다. 새 도구가 옛 도구의 수치를 재현하는지
보는 것이 검증기 역할을 한다.

5번은 40분을 쓴 뒤에 잡혔다. **샘플링 전에 "이 프롬프트가 학습에 쓰였나"를 확인했어야 한다.**
자기 학습 데이터에 자기를 샘플링하면 암기를 재는 것이지 능력을 재는 것이 아니다.

부산물로 과적합 지표가 나왔다.

```
학습에 쓴 프롬프트: 그리디 만점 106/147 (72%)
평가셋(안 쓴 것):   그리디 만점  19/33  (58%)
```

## 6. 말할 수 있는 것과 없는 것

**말할 수 있다**
- 인용 실패의 대부분은 판단이 아니라 전사 오류이고, 디코딩 제약으로 구조적으로 제거된다
- 제약을 걸면 접지 검증이 가려주던 오탐이 드러난다. 판별 문제는 보이던 것보다 크다
- 검증 가능한 보상으로 잰 상한에 여유가 있으나, **그 여유의 절반은 라벨을 쓴 신탁 값이다**

**말할 수 없다**
- 제약 디코딩이 순개선이다 — 인용에서 얻고 오탐에서 잃는다(보상 0.788 → 0.824)
- 모델이 이미 답을 알고 있다 — 유형마다 다르고, 오탐 유형은 8번 중 0~3번만 맞힌다

## 7. 다음

제약 디코딩은 **기준선으로 깔지 않고 별도 팔로 유지한다.** 한쪽을 고치며 다른 쪽을
무너뜨리므로, 그 위에 학습을 쌓으면 무엇 덕인지 말할 수 없다.

판별 9건을 겨냥하는 것은 **대조 쌍 SFT**다. 로그를 고정하고 알림만 바꿔,
로그 표면 패턴으로는 정답을 낼 수 없게 만든다. `synthesis/pairing.py`가 쌍의 로그가
바이트 단위로 같은지 강제한다. 이 검사가 없으면 생성기가 로그를 미묘하게 바꿔도 통과해
대조 학습의 전제가 조용히 무너진다.
