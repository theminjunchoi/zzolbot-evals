# 양적 정합성 규칙의 경계

> **사전 등록.** 진단과 판정 기준을 결과 보기 전에 적었다. 작성일 2026-08-29.

## 1. 기각된 가설: 로그가 길어서 무너진다

최종 팔이 틀리는 4종 중 셋이 로그 8~9줄이고 평가셋 평균은 4.2줄이다.
**"학습 데이터에 긴 로그 커버리지가 얇다"**고 보고 확인했다.

```
학습 데이터 (188건)   평균 5.8줄,  7줄 이상 46%
평가셋 (33종)         평균 4.2줄,  7줄 이상 21%
```

**틀렸다. 학습 데이터가 오히려 더 길다.**

값싼 확인이 비싼 작업을 막았다. 예정대로면 "긴 시나리오 40종 생성 + 재학습"에
반나절을 썼을 텐데, 이미 46%가 긴 데이터에 더 넣는 헛수고였다.

## 2. 실제 원인: 줄 수 대 알림 건수의 비율 감각

길이별 정답률을 보면 효과는 실재한다.

| 로그 길이 | 정답률 |
|---|---|
| 2~4줄 | 20/21 (95%) |
| 5~6줄 | 5/5 (100%) |
| **7줄 이상** | **5/7 (71%)** |

그런데 실패 2종의 사유가 **글자 하나까지 같다.**

> 로그 타임스탬프가 알림 발생 시점의 '최근 5분'과 일치하지 않고,
> **로그 수가 알림에서 언급된 급증 규모를 설명하기에 부족**

시스템 프롬프트의 **양적 정합성 규칙**이다.

> 알림이 말하는 규모를 로그 샘플이 설명할 수 있는지 확인하라. 표본이 한두 줄뿐이고
> 서로 시간이 동떨어진 산발적 에러라면 급증의 근거가 되지 못한다.
> **단, 샘플이 알림 시각과 정합하는 좁은 시간대에 몰려 반복된다면 표본 수가 알림
> 건수보다 적어도 정상적인 근거다.**

**단서 조항이 있는데 모델이 무시한다.**

### 결정적 증거: 같은 알림, 줄 수만 다름

| 시나리오 | 로그 | 알림 건수 | 시간창 | 결과 |
|---|---|---|---|---|
| `error-spike-nunchi-consumer` | **10줄** | 41건 | 3.1분 | **OK** |
| `error-spike-roomjoin-current-window` | 9줄 | 39건 | 4.2분 | **실패** |
| `error-spike-cardgame-select-burst` | 8줄 | 36건 | 3.6분 | **실패** |

셋 다 `AppErrorLogSpike`이고 알림 문구가 같은 템플릿이다. **로그가 많을수록 맞힌다.**
10줄은 통과하고 8~9줄은 "표본 부족"으로 기각한다.

**모델이 줄 수 대 알림 건수의 비율로 판단하고 있고 임계가 잘못 잡혔다.**

## 3. 커버리지 문제가 아니다

```
학습 데이터에서 '5분 이내 5줄 이상' 패턴: 48건, 전부 "예"
평가셋에서 같은 패턴:                      9종, 전부 "예"
```

**패턴은 이미 48건 있고 전부 양성이다.** 같은 것을 더 넣어도 소용없다.

문제는 **모델이 시간 분포가 아니라 줄 수로 판단한다**는 것이다.
학습 데이터가 그 구별을 가르치지 않는다.

교차표를 보면 왜 그런지 보인다.

| 학습 데이터 | 예 | 아니오 | 예 비율 |
|---|---|---|---|
| 짧은 로그 (~6줄) | 19 | 83 | **19%** |
| 긴 로그 (7줄+) | 79 | 7 | **92%** |

**길이와 판정이 얽혀 있다.** 모델이 "길면 예"라는 지름길을 배울 수 있는 구조다.
실제로 지름길을 배우진 않았지만(긴 양성에서 틀린다), **줄 수를 신호로 쓰게 만든
데이터 설계인 것은 분명하다.**

## 4. 처방: 시간 분포 대조 쌍

**알림과 로그 내용을 고정하고 타임스탬프만 바꾼 쌍**을 만든다.

```
-a : 로그 8줄, 3분 안에 몰림      →  예    (급증의 근거)
-b : 같은 로그 8줄, 6시간에 흩어짐 →  아니오 (산발적 에러)
```

**줄 수가 같으므로 줄 수로는 둘을 구별할 수 없다.** 시간 분포를 봐야만 맞힌다.

앞서 만든 대조 쌍(로그 고정, 알림 변경)과 대비되는 두 번째 유형이다.
`synthesis/pairing.py`에 **시간 대조 쌍** 검사를 추가한다.

| 쌍 유형 | 고정 | 변경 | 가르치는 것 |
|---|---|---|---|
| 알림 대조 (기존) | 로그 | 알림 | 알림과 로그의 관계 |
| **시간 대조 (신규)** | **알림 + 로그 내용** | **타임스탬프** | **시간 분포** |

### 구성 목표

| 종류 | 건수 |
|---|---|
| 시간 대조 쌍 | 20쌍 = 40건 |
| 로그 줄 수 | 5, 6, 7, 8, 9줄을 고르게 |
| 알림 건수 | 30~45 (임계 30/5m 부근) |

## 5. 사전 등록 판정 기준

주 종점은 평균 보상이고, **핵심 판정은 길이별 정답률**이다.

| 판정 | 조건 |
|---|---|
| **성공** | **7줄 이상 정답률 5/7 → 7/7** AND 짧은 로그 정답률 유지(25/26 이상) |
| 부분 | 7줄 이상이 6/7로 오르나 짧은 쪽이 하락 |
| 실패 | 7줄 이상 그대로 → 비율 감각 가설 기각 |

### 결과 보기 전 예측

**부분 성공을 예상한다.** 근거는 둘이다.

1. 시간 대조 쌍도 SFT에서는 **암묵적 압력**일 뿐이다. 앞선 알림 대조 쌍이 그래서
   판정 보류로 끝났다(통제군 대비 1건 차이, p=0.75)
2. 40건은 전체 228건의 18%다. 앞선 대조 쌍(23%)보다 작다

**빗나가면 좋다.** 시간 대조가 알림 대조보다 강하다는 뜻이고,
그건 "무엇을 대조시키느냐가 중요하다"는 더 유용한 발견이다.

## 6. 데이터 만들기에서 걸러진 것

```
생성 40건 → 스크리너 38 → 교사 32 → 쌍 유지 28건 (14쌍)
```

**탈락 4건이 전부 `WsConnectionFailuresHigh`였고 사유가 같다.**

> 로그에 'WS', 'WebSocket', '연결 실패'를 직접 가리키는 문자열이 전혀 없습니다.

WS 연결 실패 알림에 WS를 언급하지 않는 로그를 붙인 것이라 **채점 기준의 주장이 로그로
뒷받침되지 않는다.** 스크리너가 하나, 교사가 셋을 독립적으로 잡았다. 두 겹의 필터가
같은 결함을 잡아낸 셈이라 파이프라인이 제대로 작동했다.

**탈락이 "예" 쪽에 몰렸다.** 그대로 두면 47%가 되어 RFT 실패와 같은 함정에 빠진다.
짝 잃은 4건을 버려 **14쌍 완전 균형(예 14 / 아니오 14)**으로 맞췄다.

### 시그니처를 또 고쳐야 했다

**시간 대조 쌍이 전부 중복으로 판정됐다.** 시그니처가 타임스탬프를 안 보므로 a와 b의
뼈대가 같아진다. 이대로 적재하면 b쪽 20건이 통째로 탈락했을 것이다.

로그 시간 구간(5분 이내 / 60분 이내 / 그 이상)을 뼈대에 넣어 고쳤다. 내부 중복 10건 → 0건.

**세 번째로 같은 종류의 문제다.**

| 대조 쌍 유형 | 바꾸는 축 | 시그니처에 없어서 생긴 문제 |
|---|---|---|
| 알림 대조 | 알림 본문 | 알림 요약과 설명을 추가 |
| 시간 대조 | 타임스탬프 | 시간 구간을 추가 |

**대조가 바꾸는 축은 반드시 뼈대에 들어가야 한다.** 코드 주석에 원칙으로 못박았다.

## 7. 결과: 표적은 맞혔고 다른 데서 잃었다

학습 데이터 216건(v6 188 + 시간 대조 28), 894스텝, 잘림 0.

### 겨냥한 것은 100% 회수

```
error-spike-cardgame-select-burst      0.50 → 1.00
error-spike-roomjoin-current-window    0.50 → 1.00
```

**"좁은 시간창에 몰린 로그를 표본 부족으로 기각하던" 두 종이 정확히 고쳐졌다.**
진단이 맞았고 시간 대조 쌍이 그 축에서 작동했다.

### 그런데 짧은 로그가 무너졌다

| 길이 | v6c | v7c |
|---|---|---|
| 2~4줄 | **20/21** | **17/21** |
| 5~6줄 | 5/5 | 4/5 |
| **7줄 이상** | 5/7 | **6/7** |

| | v6c | v7c |
|---|---|---|
| 보상 | **0.955** | 0.909 |
| 인용 | 13/15 | **14/15** |
| 오탐 | **1/18** | **5/18** |

**긴 로그는 올랐는데 짧은 로그가 3종 떨어졌고 오탐이 1에서 5로 늘었다.**

### 사전 등록 판정: 부분 성공

```
성공 = 7줄 이상 7/7  AND  짧은 로그 25/26 이상
결과 = 7줄 이상 6/7  AND  짧은 로그 21/26
```

**결과 보기 전에 적은 예측이 그대로 맞았다.**

> 부분 성공을 예상한다. 시간 대조 쌍도 SFT에서는 암묵적 압력일 뿐이다.

### 왜 짧은 로그가 무너졌나

시간 대조 쌍의 "예" 쪽이 전부 **"몰려 있으면 근거"**를 가르친다. 그것이 일반화되면서
짧고 흩어진 로그도 근거로 인정하게 됐다. 오탐 1 → 5가 그것이다.

## 8. 네 번째로 같은 구조다

이 프로젝트에서 개입할 때마다 반대편이 밀렸다.

| 시도 | 겨냥 | 대가 |
|---|---|---|
| 1차 SFT | 인용 3/15 → 11/15 | 오탐 17% → 44% |
| 2차 SFT | 오탐 44% → 17% | 인용 11 → 10 |
| RFT | (헤드룸 회수) | 인용 9 → 7 |
| DPO | (경계 학습) | 오탐 1 → 5 |
| **시간 대조** | **긴 로그 5/7 → 6/7** | **짧은 로그 20 → 17** |

**다섯 번 다 같다. 한쪽을 겨냥하면 반대쪽이 밀린다.**

이것이 우연이 아닌 이유는 판정이 **이진 결정 하나**이기 때문이다. 모델에는 "근거를
얼마나 쉽게 인정하는가"라는 임계값이 하나 있고, 어떤 개입이든 그 임계값을 움직인다.
표적이 무엇이든 반대편 오답이 따라온다.

**깨는 방법은 임계값을 옮기는 것이 아니라 판별을 좋게 하는 것이다.** 대조 쌍이 그
시도였고, 두 번(알림 대조, 시간 대조) 다 **표적 축은 개선하고 반대편을 잃었다.**
즉 대조 쌍도 결국 임계값을 옮겼다.

## 9. 최종 팔은 그대로 v6c다

```
v6c  보상 0.955  인용 13/15  오탐 1/18   ← 최종
v7c  보상 0.909  인용 14/15  오탐 5/18
```

인용은 v7c가 낫지만 오탐 손해가 크다. **표적 2종을 회수하고 짧은 로그 3종과 오탐 4종을
잃었으므로 순손실이다.**

## 10. 말할 수 있는 것과 없는 것

**말할 수 있다**
- 실패 사유를 읽고 진단한 축(양적 정합성 경계)을 겨냥해 **표적 2종을 정확히 회수**했다
- 값싼 확인(10분)이 틀린 가설(로그 길이 커버리지)을 기각하고 정확한 표적을 줬다
- **개입이 임계값을 옮긴다**는 것이 다섯 번째로 재현됐다

**말할 수 없다**
- 시간 대조 쌍이 판별을 좋게 했다 — 표적은 올랐으나 반대편이 내려가 순손실이다
- 이 결과가 시드에 재현된다 — 시드 하나로만 돌렸다
