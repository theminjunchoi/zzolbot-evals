# 33. 배포 대상 ARM CPU에서의 속도

리포트 32번이 "제약을 걸면 Q8_0과 Q4_K_M이 품질로 구별되지 않으니 크기와 속도로 정한다"로
끝났다. 크기는 알고 있었고 **속도가 마지막 축**이었다. 그 축을 실제 배포 대상에서 쟀다.

**사전 등록 대신 리포트 32번 10절의 예측이 이 측정의 기준선이다.** 거기에 "ARM CPU는 메모리
대역폭이 병목이라 Q4가 유리할 수 있고, 차이가 크면 결정이 뒤집힌다"고 적어뒀다.

## 1. 환경

| | |
|---|---|
| CPU | Neoverse-N1 4코어 (Ampere Altra) |
| 메모리 | 23GiB, 측정 시점 15GiB 여유 |
| 부하 | 측정 전 load 0.11 |
| 동거 | 같은 호스트에 컨테이너 21개가 이미 떠 있다 |

**호스트를 다른 것과 공유한다.** 그래서 컨테이너 코어를 `--cpus`로 묶고 `nice -n 10`을 걸었다.
서버는 루프백에만 바인딩했다.

## 2. 측정 방법

**실제 서빙 경로로 쟀다.** `llama-server`에 GBNF 제약을 건 요청을 보내고 서버가 돌려주는
`timings`를 읽는다. 합성 벤치마크가 아니라 배포되면 실제로 도는 그 경로다.

시나리오는 로그 줄 수가 서로 다른 다섯 종을 골랐다(2, 2, 4, 9, 10줄). 프롬프트 길이가
1,188~2,574토큰으로 벌어져 길이 효과가 드러난다.

## 3. 결과: 알림 한 건 처리 시간 (초)

| 팔 | 로그 2줄 | 2줄 | 4줄 | 9줄 | 10줄 | 피크 메모리 |
|---|---|---|---|---|---|---|
| Q4_K_M 2코어 | 60.8 | 63.9 | 86.1 | 134.8 | 138.8 | 1.94GiB |
| Q8_0 2코어 | 51.5 | 53.9 | 66.5 | 118.2 | 121.0 | 2.22GiB |
| Q4_K_M 4코어 | 30.8 | 31.9 | 42.2 | 68.2 | 69.9 | 1.33GiB |
| **Q8_0 4코어** | **24.8** | **26.2** | **33.3** | **58.9** | **59.7** | 1.93GiB |

**Q8_0이 두 코어 수 모두에서 빠르다.**

## 4. 왜 Q8이 빠른가

단계를 나눠 보면 방향이 갈린다.

| 2코어 | 프롬프트 처리 | 생성 |
|---|---|---|
| Q4_K_M | 30~33 tok/s | 7.2~8.6 tok/s |
| Q8_0 | **45~52 tok/s** | 6.7~7.7 tok/s |

**생성은 Q4가 빠르고 프롬프트는 Q8이 빠르다.** 둘의 병목이 다르기 때문이다.

- 생성은 토큰마다 가중치를 한 번씩 훑어 **메모리 대역폭**이 병목이다. 작은 쪽이 유리하다
- 프롬프트는 여러 토큰을 한꺼번에 곱해 **연산**이 병목이다. ARM의 int8 내적 명령이 Q8_0
  커널에 직접 쓰이는데, Q4_K_M은 역양자화를 거쳐야 해서 느리다

이 워크로드는 **프롬프트가 1,188~2,574토큰이고 생성은 207~432토큰**이다. 긴 쪽이 프롬프트라
총 시간이 Q8 쪽으로 기운다. 시스템 프롬프트와 로그 샘플이 입력의 대부분을 차지하는 구조가
그대로 반영된 것이다.

코어를 2에서 4로 늘리면 프롬프트가 1.9배, 생성이 2.1배 빨라진다. 거의 선형이다.

## 5. 예측 대조: 절반 맞았다

> 리포트 32번: ARM CPU는 메모리 대역폭이 병목이라 Q4가 유리할 수 있다

**생성에서는 맞고 프롬프트에서는 틀렸다.** 그리고 이 워크로드는 프롬프트가 지배적이라
결론이 반대로 나왔다.

빗나간 원인은 "CPU 추론 = 대역폭 병목"을 한 덩어리로 본 것이다. 단계마다 병목이 다르고,
어느 단계가 지배적인지는 **입출력 길이 비율**이 정한다. 그 비율을 보지 않고 일반론을 적용했다.

## 6. 결정

**Q8_0을 쓴다.** 세 축이 전부 Q8을 가리키거나 최소한 반대하지 않는다.

| 축 | 판정 |
|---|---|
| 품질(무제약, 리포트 31) | bf16과 33종 전부 동일 |
| 품질(제약, 리포트 32) | Q4와 구별되지 않음 |
| **속도(이번)** | **Q4보다 13~20% 빠름** |
| 메모리 | 2.2GiB. 23GiB 중 문제 아님 |
| 파일 크기 | 1.6GB 대 940MB. Q4가 작지만 디스크에 여유가 있다 |

리포트 32번 10절에서 Q4로 기울었던 것을 뒤집는다. 근거는 그때 비어 있던 속도 축이다.

### 코어 수는 타임아웃과 함께 정해진다

| 구성 | 최장 처리 | 필요한 읽기 타임아웃 |
|---|---|---|
| Q8 2코어 | 121초 | 240초 |
| Q8 4코어 | 60초 | 120초 |

**2코어를 권한다.** 섀도우 호출은 다른 스레드에서 돌고 아무도 그 결과를 기다리지 않으므로
**느린 것 자체는 비용이 아니다.** 반면 코어 제한은 운영에 대한 보장이다. `--cpus 2`는 하드
캡이라 남은 2코어가 항상 확보된다.

대신 읽기 타임아웃을 240초로 올려야 한다. 지금 기본값 120초는 Q8 2코어의 최장 121초에
걸린다. **긴 알림일수록 잘리는데, 긴 알림이 비교에서 가장 값진 표본이다.**

## 7. 곁가지: 토큰 상한은 두 키가 다 먹는다

OpenAI 호환 경로에 llama.cpp 네이티브 키를 보내고 있어 무시될 수 있다는 지적이 있었다.
실측했다.

```
n_predict=16  -> 생성 16 토큰
max_tokens=16 -> 생성 16 토큰
```

이 버전에서는 둘 다 작동한다. 다만 서버를 올리면 달라질 수 있으므로 둘 다 보내는 편이 싸다.

## 8. 말할 수 있는 것과 없는 것

**말할 수 있다**

- **Q8_0이 Q4_K_M보다 총 처리 시간이 13~20% 짧다.** 두 코어 수 모두에서 그렇다
- **그 차이는 프롬프트 처리에서 나온다.** 생성만 보면 Q4가 근소하게 빠르다
- 알림 한 건이 Q8 2코어에서 52~121초, 4코어에서 25~60초 걸린다
- 피크 메모리가 2.3GiB를 넘지 않는다
- 코어 2에서 4로의 확장이 거의 선형이다(1.9~2.1배)
- 토큰 상한은 `n_predict`와 `max_tokens` 둘 다 이 버전에서 작동한다

**말할 수 없다**

- **이 수치가 운영 중 부하에서도 성립한다** - 측정 시 load 0.11이었다. 트래픽이 있을 때
  같은 값이 나오는지는 재지 않았다
- **섀도우가 운영 지연에 영향을 주지 않는다** - 측정 중 앱 응답 시간을 같이 재지 않았다.
  코어를 하드 캡으로 묶었으므로 구조적으로는 보호되지만 실측은 아니다
- 품질이 ARM에서도 같다 - 속도만 쟀다. 부동소수점 누적이 달라 출력이 갈릴 수 있고,
  실제로 같은 시나리오에서 생성 토큰 수가 Metal 측정과 다르다
- 다섯 종이 대표적이다 - 로그 줄 수로만 골랐다
