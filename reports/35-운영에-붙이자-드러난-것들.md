# 35. 운영에 붙이자 드러난 것들

리포트 34번에서 자체 모델을 zzol 알림 분석에 섀도우로 붙였다. 이 리포트는 **그것을 실제로
켜기까지 무엇이 깨졌는지**의 기록이다. 비교 데이터는 아직 한 건이다. 그 한 건을 얻는 데 버그
다섯 개를 고쳐야 했다.

## 1. 결론부터

**섀도우가 돈다.** 2026-09-22, 첫 성공 기록이다.

| 항목 | 값 |
|---|---|
| 권위(Gemini) 근거 판정 | true |
| 자체 모델 주장(접지 전) | true |
| 자체 모델 접지 후 | true |
| 자체 모델 지연 | 112.7초 |
| 로그 샘플 | 8건 |

두 모델의 요약이다. 같은 입력을 받았다.

> **Gemini**: dev 환경에서 ERROR 로그가 급증했으며, `/minigames/scores` URI에 대한 POST
> 요청에서 `HttpRequestMethodNotSupportedException` 오류가 반복적으로 발생하고 있습니다.
>
> **자체 모델**: dev ERROR 로그가 급증했으며, 로그에서 POST 요청에 대한
> HttpRequestMethodNotSupportedException 오류가 반복적으로 발생하고 있습니다.

자체 모델이 URI를 짚지 못했다. 판정과 인용은 맞다. 표본 한 건으로 말할 수 있는 것은 여기까지다.

## 2. 다섯 번 깨졌다

순서대로 나왔고, 앞의 것을 고쳐야 뒤의 것이 보였다. **하나도 단위 테스트가 잡지 못했다.**

| # | 무엇이 깨졌나 | 왜 테스트가 못 잡았나 |
|---|---|---|
| 1 | 설정 record에 생성자를 하나 더 얹어 컨텍스트 기동 실패 | 컨텍스트를 띄우는 테스트가 없었다 |
| 2 | 프롬프트를 옮기며 판정 규칙 3개 유실 | "옮기기만 했다"고 믿고 원문과 대조하지 않았다 |
| 3 | 로그의 탭이 JSON 파싱을 깨뜨려 **운영 분석이 버려짐** | 골든셋에 탭이 없다 |
| 4 | 응답을 Jackson 2 타입으로 받아 읽기 전건 실패 | 클라이언트를 목으로 대체해 컨버터를 안 탔다 |
| 5 | 출력이 토큰 상한에서 잘려 JSON이 안 닫힘 | 골든셋 출력이 짧아 상한에 안 닿았다 |

3번은 **자체 모델과 무관하게 운영에서 이미 손해를 내고 있었다.** Gemini가 근거를 정확히 찾고
원인 가설까지 맞혔는데 파싱에서 버려졌다. 섀도우를 붙이지 않았으면 발견하지 못했을 것이다.

## 3. 골든셋이 현실을 대표하지 않는다

이게 이 리포트의 본론이다. 다섯 개 중 셋(3, 5번과 프롬프트 크기 초과)이 **같은 원인**이다.

| | 골든셋 33종 | 실제 알림 |
|---|---|---|
| 프롬프트 최대 | 2,574토큰 | **13,364토큰** |
| 로그 샘플 최장 | 386자 | 800자 초과 |
| 탭 포함 샘플 | 0건 | 스택 트레이스마다 |
| 스택 프레임 4개 이상 | 0건 | 25프레임 |
| 모델 출력 | 440토큰대 | 상한 700에서 잘림 |

**내가 손으로 쓴 시나리오에는 스택 트레이스가 한 건도 없다.** 깔끔한 한 줄짜리 로그만 넣었다.
리포트 29번에서 "두 번째 입력 사각"을 말했는데, 그때는 어떤 알림이 로그를 못 얻는지의 문제였다.
여기서 드러난 것은 **얻은 로그의 모양 자체가 다르다**는 것이다.

시사점이 둘이다.

- **모델은 스택 트레이스가 든 로그를 학습에서 본 적이 없다.** 학습 데이터가 골든셋에서 나왔다.
  실전 성능이 골든셋 점수보다 낮을 수 있고, 그 차이가 섀도우로 재려던 값이다.
- **측정값 자체는 유효하다.** 정규화를 넣기 전 골든셋 140건을 전수 검사해 탭 0건, 800자 초과
  0건, 스택 4프레임 이상 0건을 확인했다. 정규화가 골든셋 입력을 한 글자도 바꾸지 않는다.
  이 불변식은 팀 레포 테스트로 고정했다.

## 4. 고친 방식

**입력을 자르지 않고 정규화했다.** 두 조건을 같이 만족해야 했다. 권위 모델(Gemini)의 성능이
떨어지면 안 되고, 두 모델의 비교가 성립해야 한다.

Loki 조회 직후 한 번만 다듬고 **두 모델과 인용 검증, 문법 생성이 같은 문자열을 본다.**
버리는 것은 반복되는 스택 프레임이지 근거가 아니다. 예외 메시지와 발생 위치는 앞 3프레임으로
남는다. 프롬프트가 13,364에서 2,820토큰으로 내려갔다.

**출력은 문법으로 묶었다.** 상한만 올리면 언젠가 또 넘는다. 제안 조치 배열과 문자열 길이에
제한이 없어 출력이 원리적으로 무한하기 때문이다. GBNF의 반복 횟수와 길이 제한을 써서
요약 200자, 가설 200자, 조치 150자 3개로 막았다.

## 5. 배포 전에 재는 것으로 바꿨다

네 번을 고치고 배포하고 또 깨진 뒤에야 순서를 바꿨다. 다섯 번째는 **배포 전에 실제 서버에서
최악을 태웠다.**

스택 25프레임이 붙은 ERROR 20건으로 프롬프트를 만들어 보냈다.

```text
finish_reason: stop
프롬프트 4,234토큰 91.4초 / 생성 146토큰 17.2초 / 합계 108.7초
JSON 파싱 성공, 조치 3개(상한)
```

`finish_reason`이 `length`가 아니라 `stop`인 것이 핵심이다. 문법이 실제로 묶었다는 뜻이다.
이론적 최악도 실측 처리량으로 계산해 타임아웃을 정했다(프롬프트 36.7 tok/s, 생성 8.4 tok/s,
최악 350초 → 타임아웃 420초).

**이걸 처음부터 했으면 배포를 네 번 덜 했다.**

## 6. 남은 것

- **비교 데이터 축적.** 실제 알림은 prod에만 온다. Alertmanager의 수신기가 prod 활성 색만
  바라본다. prod 승격이 남았다.
- **표본 1건으로는 아무 말도 못 한다.** 판정이 갈리는 비율, 갈릴 때 누가 맞는지가 다음 질문이다.
- **평가 레포의 Python 문법에는 길이 상한이 없다.** 골든셋 출력이 440토큰대라 상한이 걸리지
  않지만 두 구현이 갈라진 것은 사실이다.

## 7. 다음 리포트에서 답할 질문

실제 알림에서 두 모델의 판정이 얼마나 갈리는가. 그리고 **갈릴 때 누가 맞는가.**
합성 33종에서는 서로 다른 것을 틀렸다(리포트 15번). 실전에서도 그런지가 관심사다.

여기에 하나가 더 붙었다. **골든셋에 없던 입력 형태에서 자체 모델이 얼마나 버티는가.**
