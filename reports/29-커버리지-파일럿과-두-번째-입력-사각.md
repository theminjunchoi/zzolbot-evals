# 29. 커버리지 파일럿: 수율 20%, 그리고 봇의 두 번째 입력 사각

리포트 27번에서 확대의 근거를 검정력에서 커버리지로 바꿨고, 28번에서 지표 부재 계열을
기각했다. 남은 앱 계층 4종으로 파일럿을 돌렸다.

**생존율보다 탈락 사유가 값졌다. 실제 운영 사고 하나의 원인을 설명한다.**

## 1. 결과: 20건 시도, 4건 생존 (20%)

| 알림 | 축 | 기대 판정 | 로그 |
|---|---|---|---|
| ErrorBudgetBurnFast | positive-dense | 예 | 8줄 |
| ErrorBudgetBurnFast | positive-dense | 예 | 6줄 |
| IpBanRateSpike | unrelated-trap | 아니오 | 2줄 |
| WsConnectionFailuresHigh | unrelated-trap | 아니오 | 3줄 |

**양성 2 / 음성 2로 균형이 맞았다.** 리포트 28번에서 걱정한 불균형은 이 배치에서는
일어나지 않았다.

**수율 20%는 과거(24~46%)보다 낮다.** 새 알림이라 카탈로그 재료가 얇은 것이 원인으로
보이나 표본이 작아 단정하지 못한다.

| 검증기 | 탈락 |
|---|---|
| log-line (형식) | 6 |
| rubric (정답/오답 조건 누락) | 5 |
| **error-level** | **4** |
| screen (rubric-로그 모순) | 3 |

**`CpuUsageHigh`는 4번 시도해 0건 생존이다.** 로거-스레드 궁합 위반과 rubric 누락으로
전부 떨어졌다. 카탈로그에 이 알림용 재료가 사실상 없다는 뜻이다.

## 2. 봇의 두 번째 입력 사각: 로그 레벨

`IpBanRateSpike` 탈락 4건이 전부 같은 사유다.

```
[error-level] 로그 0: 봇 입력은 ERROR만 도달 가능한데 WARN
```

생성기가 IP 차단 로그를 WARN으로 썼고 검증기가 막았다. **생성기가 맞았다.**
팀 레포를 확인하니 IP 차단 로깅이 전부 `log.warn`이다.

```java
// infra/.../ipblock/IpBlockFilter.java
log.warn("악성 경로 접근 감지 → IP 즉시 차단: ip={} uri={}", ip, uri);
log.warn("차단된 IP 접근 시도: ip={} uri={}", ip, uri);
// infra/.../ipblock/IpBlockStore.java
log.warn("IP 차단 등록: ip={} ttl={}h", ip, properties.blockTtl().toHours());
```

`log.error`가 **하나도 없다.** 봇의 쿼리는 `{environment="..."} |~ "ERROR"`다.

**봇은 IP 차단 증거를 구조적으로 볼 수 없다.**

### 리포트 28번을 일반화한다

봇의 입력 필터가 두 겹이고, **각각이 다른 것을 가린다.**

| 필터 | 가리는 것 | 영향받는 알림 |
|---|---|---|
| `environment` 라벨이 `/app/logs/application.log`에만 붙음 | **인프라 로그** | 지표 부재 계열 7종(28번) |
| `\|~ "ERROR"` | **WARN 이하 사건** | `IpBanRateSpike`, 그리고 아직 안 센 것들 |

두 경우 모두 **정답이 항상 "근거 없음"**이 된다. 봇이 게을러서가 아니라 증거가
입력에 도달하지 않아서다.

## 3. 이것이 실제 사고를 설명한다

이 프로젝트의 출발점이 된 사고가 있다.

> 2026년 7월, **IP 차단 급증 알림에 봇이 무관한 카드게임 에러 로그를 원인으로 지목한
> 일이 13건 반복됐다**(이슈 #1592).

**왜 그랬는지가 이제 설명된다.** IP 차단의 진짜 증거는 WARN이라 봇에게 도달하지 않았고,
같은 시각에 도달한 것은 무관한 앱 ERROR뿐이었다. **봇에게는 그것 말고 볼 것이 없었다.**

봇의 판단력 문제가 아니라 **입력 계약의 문제**다. 프롬프트를 고치거나 모델을 학습시켜도
근본적으로는 "근거 없음"이라고 답하게 만드는 것이 최선이고, 그 이상은 불가능하다.

**평가셋을 만들다가 제품 결함의 원인을 찾았다.** 커버리지 기준 확대의 값이 여기 있다.

## 4. 말할 수 있는 것과 없는 것

**말할 수 있다**
- 앱 계층 4종 파일럿에서 **20건 중 4건 생존(20%)**, 양성 2 / 음성 2로 균형
- **IP 차단 로깅이 전부 WARN이라 봇이 볼 수 없다.** 팀 레포 두 파일에서 확인했다
- 봇의 입력 사각이 **둘**이다. 로그 출처(인프라 제외)와 로그 레벨(WARN 이하 제외)
- **2026년 7월 IP 차단 오진 13건의 원인이 설명된다.** 판단력이 아니라 입력 계약이다
- `CpuUsageHigh`는 카탈로그 재료가 없어 4번 시도해 0건이다

**말할 수 없다**
- 수율 20%가 새 알림의 특성이다 - 20건은 작다. 과거 24~46%와의 차이가 유의한지 모른다
- **WARN 사각이 IpBanRateSpike에만 해당한다** - 다른 알림도 셀 수 있는데 **세지 않았다.**
  팀 레포의 `log.warn` 사용처를 알림별로 대조하는 작업이 남았다
- 봇의 입력 계약이 잘못됐다 - ERROR만 보는 것이 의도된 선택일 수 있다. **비용과 노이즈
  문제가 있고 팀에 확인하지 않았다**
- 생존한 4건이 골든셋에 들어갈 수 있다 - **아직 사람 검토와 중복 검사를 안 했다**
