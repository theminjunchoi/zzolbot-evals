# zzolbot-evals

**운영 모니터링 봇의 LLM이 근거 없이 원인을 지어내는 문제를 재고 고친 기록**

평가셋을 만들고, 무엇을 틀리는지 유형화하고, 그 유형만 겨냥한 학습 데이터로 소형 모델을
파인튜닝해서, 전후를 통계로 비교하는 사이클을 여러 번 돌렸다.

**결과 한 줄**: 노트북에서 도는 1.5B 모델이 **총점 45% → 85%**, 근거 인용 **20% → 87%**가 됐다.
**오탐은 6%로 Gemini와 같다.**

| | 총점 | 인용 | 오탐 |
|---|---|---|---|
| Gemini 2.5 Flash (API) | 91% | 100% | **6%** |
| **로컬 1.5B (최종)** | **85%** | **87%** | **6%** |
| 로컬 1.5B (학습 전) | 45% | 20% | 83% |

**미리 밝혀둘 것**: 총점과 인용은 Gemini가 앞선다. 다만 **두 시스템은 서로 다른 것을 틀리고**,
겹치는 실패는 33종 중 1종뿐이다. [상세는 아래 Gemini 비교에 적었다](#그래서-gemini보다-좋아졌나).

## 1. 무슨 문제인가

[zzol](https://zzol.site)에는 **zzolbot**이라는 운영 봇이 있다. 서버에 이상이 생기면
이렇게 움직인다.

```
서버 이상 감지 (Alertmanager)
   → 그 시각 근처의 에러 로그를 긁어옴
   → LLM에게 "이 알림의 원인이 뭐냐"고 물어봄
   → 답변을 Slack에 올림
```

편리하지만 **위험한 실패 모드**가 하나 있다. LLM은 모르면 모른다고 하지 않고
**그럴듯한 이야기를 지어낸다.**

실제 사례로 보면 이렇다.

<table>
<tr><td width="50%">

**봇에게 주어지는 것**

알림:
> `DiskUsageHigh` - 디스크 사용률이 88%.
> 로그 정리 또는 디스크 확장 필요.

같은 시각의 에러 로그 2줄:
```
[14:10:05] [ERROR] 정산 스트림 처리 실패
[14:25:42] [ERROR] QR 코드 생성 실패
```

</td><td width="50%">

**정답**

> 근거 발견: **아니오**

로그는 전부 애플리케이션 로직 오류다.
**디스크 용량과 아무 상관이 없다.**
원인을 말하지 않아야 맞다.

**오답**

> "정산 처리 실패가 누적되어
> 디스크가 찼습니다"

말은 되지만 근거가 없다. 이걸 믿고
새벽에 일어나면 헛걸음이다.

</td></tr>
</table>

운영 도구에서 **틀린 답은 답이 없는 것보다 나쁘다.** 아무 말도 안 하면 사람이 직접 보지만,
그럴듯한 오진은 사람을 엉뚱한 방향으로 몇 시간 끌고 간다.

그래서 이 프로젝트가 던지는 질문은 하나다.

> **봇이 근거 없이 원인을 말하는 빈도를 어떻게 재고, 어떻게 줄이는가?**

## 2. 어떻게 접근했나

### 2-1. 채점 가능한 시험지를 만들었다 (골든셋 33종)

잘한다 못한다를 말하려면 **정답이 정해진 문제집**이 있어야 한다. 실제 zzol 인프라의
로그 형식, 알림 룰, 클래스 이름과 맞아떨어지는 시나리오 33종을 만들었다.

| | 개수 | 내용 |
|---|---|---|
| 근거 있음 | 15종 | 로그에 진짜 원인이 있다. **찾아내야** 정답 |
| 근거 없음 | 18종 | 로그가 알림과 무관하다. **모른다고 해야** 정답 |

**둘을 반반 섞은 것이 핵심이다.** 근거 있음만 모으면 무조건 원인이 있다고 답하는 모델이
만점을 받고, 근거 없음만 모으면 모르겠다만 하는 모델이 만점을 받는다. 섞어야
**진짜 변별력**이 드러난다.

실제로 이 설계가 값을 했다. 소형 모델의 첫 점수 47%를 뜯어보니, 66번 중 54번을 모르겠다고
답하고 그중 30번이 우연히 맞은 것이었다. **점수의 대부분이 실력이 아니라 전략이었다.**

### 2-2. 채점을 두 겹으로 했다

```
모델 답변
   │
   ├─ [1겹] 코드 검증 ── 인용한 로그 줄이 실제 로그에 글자 그대로 있는가?
   │                      없으면 "근거 없음"으로 강등. LLM을 안 거치는 기계적 판정
   │
   └─ [2겹] LLM 채점 ── 채점 기준과 대조해 PASS/FAIL
```

1겹이 중요한 이유가 있다. 소형 모델은 로그를 **베끼는 대신 재구성한다.**
실제로 이런 인용을 냈다.

```
진짜 로그:  [2026-08-26 14:00:05.112] [ERROR] [a1b2c3d4e5f60708090a1b2c3d4e5f60,...
모델 인용:   2026-08-26 14:00:05.112  [ERROR]  [a1b2c3d4e5f6            ← 트레이스 ID를 지어냄
```

말은 그럴듯한데 **없는 로그를 인용했다.** 코드 검증이 이런 답변 10건을 전부 잡아냈다.

### 2-3. 채점자를 먼저 검증했다

LLM에게 채점을 시키면 **채점자가 틀릴 수 있다.** 그래서 채점자부터 시험했다.

정답 답변을 일부러 망가뜨린 것(원인을 지어낸 답변, 컴포넌트를 바꿔치기한 답변,
두루뭉술하게 뭉갠 답변 등 8종)을 먹여서 잡아내는지 봤다.

| | 결과 |
|---|---|
| 명백한 오답 | 40건 중 **40건** 잡음 |
| 두루뭉술한 원인 서술 | 5건 중 **2건**만 잡음 ← 구멍 |

**한쪽으로만 느슨했다.** 채점 기준에 구체성 요건을 넣어 놓친 오답을 3건에서 0건으로 줄였다.
그러자 그전까지 노이즈로 분류하던 실패가 **일관된 실패**로 드러났다.
측정기를 조이니 있던 문제가 보이기 시작한 것이다.

## 3. 무엇을 발견하고 어떻게 고쳤나

### 3-1. 오답의 정체: 판단력이 아니라 복사 능력

소형 모델(Qwen2.5-1.5B)이 근거 있는 15종에서 뭘 하는지 갈라서 쟀다.

| 단계 | 결과 |
|---|---|
| 근거를 알아봤는가 | **13/15 (87%)** ← 잘한다 |
| 인용을 원문 그대로 옮겼는가 | **3/15 (20%)** ← 여기서 무너진다 |

**근거는 알아본다. 그런데 로그를 그대로 베끼지 못해 코드 검증에 걸린다.**
판단력이 아니라 출력 습관 문제였고, **파인튜닝이 가장 잘 고치는 종류의 실패다.**

### 3-2. 첫 번째 시도: 고쳤는데 부작용이 생겼다

로그를 글자 그대로 인용하는 행동만 겨냥해 학습 데이터 100건을 만들고 파인튜닝했다.

```
인용 성공  3/15 → 11/15   (개선 8건 / 악화 0건, p = 0.0078)
```

겨냥한 건 확실히 고쳤다. **그런데 미리 예측해둔 부작용이 나타났다.**

학습 데이터의 정답 분포가 근거 있음 79 대 근거 없음 21로 치우쳐 있었고,
그 비율을 그대로 흉내 내서 **아무 데서나 근거를 찾기 시작했다.**

```
오탐(근거 없는데 있다고 답함)  17% → 44%
```

### 3-3. 두 번째 시도: 부작용을 표적으로

근거 없음 시나리오를 더 만들어 학습 데이터 비율을 조정하고 다시 학습했다.
**비율만 바꾸고 나머지 조건은 전부 고정**해서 원인을 하나로 좁혔다.

| 학습 데이터 비율 | 인용 성공 | 오탐 |
|---|---|---|
| 79 : 21 (첫 번째 시도) | 11/15 | 44% |
| 59 : 41 | 8/15 | 11% |
| **70 : 30** | **10/15** | **17%** |

가운데 줄(59:41)만 보면 실패다. 오탐은 잡았는데 인용이 같이 떨어졌으니까.
**여기서 그냥 되돌리지 않고 한 가지를 더 봤다.**

근거를 주장한 **횟수**가 14번에서 9번으로 함께 떨어졌고,
주장했을 때의 **정확도**는 79%에서 89%로 **올랐다**.
즉 **나빠진 게 아니라 신중해진 것**이었다.

그렇다면 참을 맞히는 비율에서 거짓에 속는 비율을 뺀 값이 좋아졌을 수 있다. 계산해보니 그랬다.

| | 참을 맞힘 | 거짓에 속음 | 차이 |
|---|---|---|---|
| 학습 전 | 0.20 | 0.17 | 0.03 |
| 첫 번째 시도 | 0.73 | 0.44 | 0.29 |
| 59:41 | 0.53 | 0.11 | **0.42** |

**기준만 엄해진 게 아니라 판별 자체가 좋아졌다.** 그렇다면 두 조건을 동시에 만족하는
중간 지점이 있을 수 있다. 새 데이터를 만들지 않고 기존 데이터의 비율만 70:30으로 바꿔
다시 학습했고, 예측대로 나왔다.

**첫 번째 시도는 인용 개선을 오탐 27%p를 지불하고 샀고, 두 번째 시도는 지불 없이 얻었다.**

### 3-4. 세 번째 시도: 대조 쌍과 함정 데이터

두 번째 시도까지의 오탐은 학습 전과 같은 17%였다. **비율을 옮겨도 그 이상은 안 됐다.**
임계값이 아니라 판별을 바꿔야 했다.

두 가지를 넣었다.

**대조 쌍 19쌍.** 로그를 고정하고 알림만 바꿔, 같은 로그가 한쪽에서는 근거가 되고
다른 쪽에서는 안 되게 만들었다. 로그 표면 패턴만으로는 둘 다 맞힐 수 없다.

```
같은 로그 3줄 + OutboxDeadLetterHigh  →  근거 있음
같은 로그 3줄 + DiskUsageHigh         →  근거 없음
```

**오탐 함정 15건.** 실제로 틀리던 두 축을 겨냥했다. 알림 규모를 로그가 설명 못 하는
경우(희소 근거)와, 알림 대상이 애플리케이션 바깥인데 로그는 앱 오류인 경우(인프라 계층)다.

```
오탐  7/18 → 1/18
```

**함정 데이터가 결정적이었다.** 대조 쌍의 개별 효과는 통제군 대비 1건 차이라 판정 보류다.

### 3-5. 인용은 학습이 아니라 디코더로 고쳤다

남은 인용 실패를 뜯어보니 판단이 아니라 **전사 오류**였다. 옳은 줄을 고르고 글자를 틀린다.

```
모델 인용: [2026-08-26 14:10:05.122] [ERROR] [,] --- [pool-1-thread-4] c.g.h.RedisStreamCon...
실제 원문: [2026-08-26 14:10:05.130] [ERROR] [,] --- [pool-1-thread-4] c.g.h.RedisStreamCon...
                          ^^^ 8밀리초.  유사도 99%
```

밀리초 두 자리를 학습으로 가르치는 대신 **디코딩 단계에서 불가능하게** 만들었다.
`"evidenceLine": "` 이후 다음 토큰을 허용된 로그 줄들의 토큰 트라이로 제한한다.

```
인용  9/15 → 13/15   (학습 없음)
```

**그런데 이 제약의 가치는 모델의 판별력에 달려 있다.** 앞선 모델(허위 주장 7/18)에 걸었을
때는 오히려 손해였다. 접지 검증이 **허위 주장을 우연히 막고 있었기 때문**이다. 인용이
정확해지자 그 방어가 무력화됐다. 판별이 좋아진 모델(허위 주장 1/18)에서는 벗겨질 방어가
없어 순이득이 된다. **예측하고 실측했다.**

### 3-6. 최종 결과

<tr><th></th><th>학습 전</th><th>1차</th><th>2차</th><th>3차 + 디코더 제약</th></tr>
<tr><td><b>judge 총점</b></td><td>15/33 (45%)</td><td>19/33 (58%)</td><td>23/33 (70%)</td><td><b>28/33 (85%)</b></td></tr>
<tr><td><b>인용 성공</b></td><td>3/15 (20%)</td><td>11/15 (73%)</td><td>10/15 (67%)</td><td><b>13/15 (87%)</b></td></tr>
<tr><td><b>오탐</b></td><td>15/18 (83%)</td><td>9/18 (50%)</td><td>7/18 (39%)</td><td><b>1/18 (6%)</b></td></tr>
</table>

오탐은 접지 전 원 주장 기준이다(모델의 판별력). 봇의 실제 동작은 접지 검증을 거치므로
더 낮게 나오지만, 그 값은 인용 실패가 가려준 것이라 능력을 재기에는 부적절하다.

### 그래서 Gemini보다 좋아졌나

같은 평가셋, 같은 채점자로 나란히 놓으면 이렇다.

| | judge 총점 | 인용 통과 | 오탐 |
|---|---|---|---|
| **Gemini 2.5 Flash** (API) | **30/33 (91%)** | **15/15 (100%)** | **1/18 (6%)** |
| 1.5B 학습 전 | 15/33 (45%) | 3/15 (20%) | 15/18 (83%) |
| **1.5B 최종** | **28/33 (85%)** | 13/15 (87%) | **1/18 (6%)** |

- **총점**: 15 → 28. Gemini까지의 격차 15점 중 **13점(87%)**을 좁혔다
- **인용**: 20% → 87%. 격차의 **84%**를 좁혔다
- **오탐**: 83% → 6%. **Gemini와 동률이다**

### 총점 차이가 능력 차이와 같지 않다

**두 시스템이 서로 다른 것을 틀린다.** judge 기준 실패를 맞대어 보면 겹치는 것이 하나뿐이다.

| | 개수 |
|---|---|
| 둘 다 틀림 | **1종** |
| **Gemini만 틀림** | **2종** |
| 로컬만 틀림 | 5종 |

Gemini가 틀리는 둘은 **말을 너무 많이 해서** 틀린다. 무관한 로그를 근거로 인정하거나,
맞는 원인에 무관한 것을 끼워 넣는다. 자제하도록 학습시킨 모델이 그 축에서 유리하다.

로컬이 틀리는 다섯은 성격이 다르다. 셋이 **로그가 8~9줄로 긴 시나리오**인데, 근거를 못 찾거나
여러 오류 중 증상을 원인으로 착각한다. 평가셋 평균이 2~4줄이니 **로그가 많아지면 무너진다.**

### 애초에 Gemini를 이기는 것이 목표가 아니었다

**Gemini는 API 뒤에 있어 고칠 수 없다.** 평가로 약점을 찾아 학습 데이터로 고치고 전후를
비교하려면 루프 안에 **바꿀 수 있는 모델**이 있어야 하고, 1.5B는 성능 챔피언이 아니라
그 실험 대상이었다.

덧붙이면 이 평가셋은 원래 **Gemini를 깨려고** 만들었다. 처음엔 만점이 나와서 시나리오를
합성으로 늘렸고 그래도 91%다. 반대로 1.5B는 45%라 헤드룸이 커서 학습 효과를 보기 좋았다.

### 자체 호스팅의 두 가지 이점

**하나. 데이터가 밖으로 나가지 않는다.** 로컬 1.5B는 노트북에서 돌고 호출 비용이 0이다.

**둘. 디코더를 제약할 수 있다.** 이게 덜 알려진 쪽이다. "인용은 반드시 실제 로그 줄이어야
한다"를 **모델에게 부탁하는 대신 강제할 수 있다.** Gemini는 API 뒤에 있어 로짓을 건드릴 수
없으므로 같은 보장을 만들 방법이 없다. 부탁은 확률이고 강제는 보장이다.

인용 87% 중 상당 부분이 이 제약에서 나왔다(학습만으로는 60%였다).

### 3-7. 결과를 스스로 공격했다

학습 데이터도 합성이고 평가셋 33종 중 12종도 합성이다. 그러면 "**같은 생성기가 만든 것끼리
재서 암기를 측정한 것 아니냐**"는 반론이 가능하다.

평가셋을 갈라서 확인했다. 21종은 사람이 손으로 만들었고(**생성기 분포 밖**),
12종은 합성으로 만들었다(**분포 안**).

| | 학습 전 | 학습 후 |
|---|---|---|
| 분포 **밖** (수작업) | 3/10 | **7/10** (+4) |
| 분포 **안** (합성) | 0/5 | **3/5** (+3) |

**개선이 분포 안쪽에 몰려 있지 않고, 오히려 밖이 더 크다.** 암기 가설로는 이 방향이 안 나온다.

```

  splits.json           dev 21 / test 12 분할

  local_model.py          로컬 소형 모델 (API 대신)

harness/constrained.py  인용을 실제 로그 줄로만 생성하도록 강제하는 디코더

analysis/               채점자 검증 + 종점 측정
  mutations.py            정답을 일부러 망가뜨려 채점자를 시험
  reward.py               학습 신호와 평가 종점과 판정 기준을 겸하는 보상 함수
  endpoints.py            인용 성공률과 오탐률을 judge 없이 계산

synthesis/              시나리오 자동 생성
  validators.py           규칙 검증 10종 (형식, 스레드 이름, 시각 순서 등)
  pairing.py              대조 쌍의 로그가 바이트 단위로 같은지 검사
  screening.py            LLM 사전 검사

training/               학습 데이터 만들기
  verification.py         정답이 진짜 옳은지 검증 5종
  audit_cli.py            중복과 누출 감사 4겹
  length_guard.py         샘플이 길면 빌드를 멈춤 (버리지 않고)
  dpo.py                  DPO 손실 (mlx-lm에 없어 직접 구현)

reports/                리포트 20편. 번호 순서가 곧 작업 순서
```

평가셋 구축에서 학습 전후 비교까지 한 줄기로 이어진다.

## 6. 말할 수 있는 것과 없는 것

솔직하게 적어둔다.

**말할 수 있다**
- **오탐을 83%에서 6%로 줄여 Gemini와 동률이 됐다.** 겨냥한 축(희소 근거, 인프라 계층)의
  데이터가 작동했다
- 학습 데이터의 정답 비율이 모델의 판단 성향을 직접 좌우한다. 곡선을 세 점으로 그렸다
- 인용 실패의 대부분은 판단이 아니라 전사 오류이고, 디코딩 제약으로 구조적으로 제거된다
- **디코딩 제약의 순효과는 모델의 판별력에 달려 있다.** 예측하고 실측했다
- 시드를 바꿔도 재현되고, 생성기 분포 밖에서도 유지된다

**말할 수 없다**
- **Gemini보다 좋아졌다** - 총점과 인용은 여전히 Gemini가 앞선다(91% 대 82%, 100% 대 87%)
- **인용 87%가 학습의 성과다** - 학습만으로는 60%였고 나머지는 디코더 제약이다
- 대조 쌍이 효과가 있었다 - 통제군 대비 1건 차이라 노이즈와 구별되지 않는다(p = 0.75)
- 총점 상승이 통계적으로 확정됐다 - n=33에서 이 효과 크기로는 p < 0.05가 안 나온다
- 특정 시나리오를 고쳤다 - 시드를 바꾸면 어느 시나리오를 맞히는지가 달라진다

**한계**
- 평가셋이 33종(근거 있음 15 / 없음 18)으로 작다. 모든 검정이 이 크기 위에 서 있다
- **남은 실패의 3분의 2를 코드로 채점하지 못한다.** 원인 오진과 환각은 LLM 채점자만
  잡을 수 있어, 검증 가능한 보상으로 학습시킬 수 없다
- 로그가 8~9줄로 길어지면 무너진다. 평가셋 평균은 2~4줄이다
